# frontend do 2ag

interface web do 2ag, pensada primeiro para o celular. consome a api do [`backend`](../backend/README.md).

## tecnologias

- react 19 e vite 8
- react router 8, com cada tela carregada sob demanda
- gráfico de evolução em svg feito à mão, sem biblioteca
- react-icons nos ícones do menu
- css puro, com css modules nos componentes novos

## rodando

```bash
cd frontend
npm install
npm run dev
```

abra http://localhost:5173. o vite repassa as chamadas de `/api` para a api em `http://localhost:8080`, então a api precisa estar rodando. se ela estiver em outra porta, crie o arquivo `frontend/.env.local` com a linha `API_URL=http://localhost:8081`. esse arquivo fica fora do git.

| comando | o que faz |
| :--- | :--- |
| `npm run dev` | servidor de desenvolvimento |
| `npm run build` | build de produção em `dist/` |
| `npm run preview` | serve o build de produção |
| `npm run lint` | eslint |
| `npm test` | testes com vitest e testing library |

## navegação

- **layout por perfil:** paciente, prescritor e administrador têm menu próprio. no celular o menu vira uma barra inferior. na barra do paciente, as telas que não têm item nela (*Prescrições*, *Histórico*, impressão, anamnese e escalas) marcam o *Início*, para a pessoa não perder onde está, e o menu lateral continua marcando o item da tela, do mesmo jeito que o progresso de um paciente marca *Pacientes* na barra do prescritor. no celular o menu lateral some e o leitor de tela só tem a barra, então esse *Início* vai com `aria-current="true"` e é lido como o item atual, e não como a página aberta, que fica para o *Início* do próprio painel (26/11/2026)
- **rotas protegidas:** as regras ficam em `app/route-guards.js` e rodam antes da tela abrir. quem não tem acesso volta para a própria tela inicial, e quem não está logado vai para o login com `?voltar=` e, depois de entrar, volta para a tela que pediu. a api confere tudo de novo, porque esconder rota não protege dado
- **carregamento sob demanda:** cada tela é um arquivo separado. enquanto a próxima tela baixa, a atual continua visível e uma barra fina aparece no topo
- **transição:** cada tela nova entra com um fade curto, desligado para quem pede menos movimento no sistema operacional
- **foco do teclado:** botões e links mostram um anel verde cheio (`--focus-ring` em `styles/tokens.css`), separado do botão por uma folga da cor do cartão, que passa de 3:1 sobre o fundo nos dois temas; o campo de texto mostra a borda verde com um halo leve (`--focus-halo`). o `scroll-padding` do `html` (`index.css`) faz o navegador rolar o campo que recebe o foco do tab para fora da barra de ações presa no pé dos formulários e, no celular, também do menu de baixo e do cabeçalho. o navegador só rola quando o campo está fora da janela, e o campo que já estava na janela, mas atrás da barra, ficava meio escondido: desde 13/11/2026 o layout confere o campo que recebe o foco (`utils/focus-above-bars.js`) e sobe a página só o bastante para ele aparecer inteiro acima das barras marcadas com `data-bottom-bar` (a de ações dos formulários, a da anamnese e o menu de baixo do celular), com uma folga de 12 px. o campo mais alto que o espaço livre sobe só até o topo dele aparecer. do mesmo jeito, o campo atrás de uma barra presa no alto, marcada com `data-top-bar` (o contador das escalas), desce só o bastante para aparecer. na opção desenhada, como o cartão e a nota da régua das escalas e o `ChoiceCard`, o radio ou a caixa de marcar de verdade fica escondido no alto do rótulo, então a conta vale para o rótulo inteiro, e o cartão aparece todo, com o anel de foco (17/11/2026)
- **borda dos controles:** campo de texto, seletor, área de texto, cartão de opção, bolinha e caixa de marcar vazias, nota da régua e a linha das faixas do gráfico usam `--color-control-border` (`styles/colors.css`), que passa de 3:1 sobre o cartão, o fundo da página, o campo travado e as três faixas da régua de dor, nos dois temas. `styles/control-border.test.js` refaz a conta da WCAG e confere quem usa o token. o contorno dos cartões e a grade do gráfico continuam com `--color-border` e `--color-chart-grid`, mais claros. o campo recusado fica com a borda dobrada na cor de erro, porque só a cor já não separa do campo em repouso (20/11/2026)

- **rota inexistente e erro inesperado:** caem numa página própria, com caminho de volta ao início
- **título da aba:** cada rota leva um nome fixo no `handle` dela, em `app/router.jsx`, e a raiz das rotas (`app/page-title.jsx`) escreve esse nome no título da página com o nome do sistema, como *Agenda · 2AG*. por ficar na raiz, vale também para as telas de fora do layout (entrar, criar conta, recuperar senha, senha nova e confirmação de e-mail). as telas de erro, de página não encontrada e de sem conexão levam o próprio nome (`StatusTitle`), e sair delas devolve o nome da rota. o título fica nas abas e no histórico do navegador, que pode ser de um computador de mais gente, então nunca é montado com dado: não leva nome de paciente, nome de escala, diagnóstico nem data, e a tela de uma escala é só *Escala · 2AG*. enquanto há na tela um campo marcado com erro por um envio recusado (`aria-invalid`), o título começa com *Erro:*, como em *Erro: Perfil · 2AG*. o prefixo acompanha o campo marcado, e não uma contagem de recusas: sai quando o envio seguinte é aceito, quando a pessoa troca de tela e quando o modal do formulário fecha, e o campo da tela escondida pelo termo ou pelo login por cima não conta. a recusa que não marca campo nenhum, como a senha errada na entrada, continua só no aviso (20/11/2026)
- **erro de campo no envio:** o envio recusado leva o foco ao primeiro campo com erro (`useFocusFirstError`, em `components/form/focus-first-error.js`), e a mensagem ligada pelo `aria-describedby` é lida junto com o campo (decisão de 13/11/2026). vale para os modais com formulário (anulação, marcar e remarcar consulta, e na administração novo prescritor, senha nova, correção de e-mail e correção de dados), o perfil, o cadastro, a tela de senha nova, a tela do termo, o pedido de consulta do paciente e o registro da consulta, e desde 17/11/2026 a escala do paciente e o Mini-Exame, onde o item obrigatório em branco também leva o foco. desde 18/11/2026 vale também para a prescrição: o erro de um canabinoide marca o campo da linha dele na composição, e a recusa que não marca campo nenhum (o isolado com dois canabinoides, a recusa da api que não é de campo) vai com o motivo para o aviso de cima, e a tela rola até ele, porque o botão de emitir fica preso no pé da tela. a modalidade (presencial ou remota) vem sem nada marcado no pedido do paciente, na *Nova consulta* da agenda e no registro de consulta, e enviar sem escolher marca o campo e leva o foco até ele, com a mesma mensagem da api (decisão de 14/11/2026, revisão das regras R24). nos modais da administração, a recusa que não é de nenhum campo continua no aviso, com `role="alert"`

não puxa o foco. no convite de paciente, o *Gerar link de convite* dá lugar ao link, que recebe o foco, como cada link gerado depois, e cancelar um convite em aberto tira a linha com o botão, então o ## sessão

a sessão fica num cookie `httpOnly`, que o javascript não enxerga. o `main.jsx` pergunta à api quem está logado antes de montar as rotas, e `getLoggedUser()` devolve esse usuário para qualquer tela. um `401` com alguém logado quer dizer que a sessão venceu (2 horas parada ou 12 horas depois do login): dentro do layout a página não recarrega, o `api.js` guarda o envio que recebeu o `401` só na memória e o layout abre um login por cima da tela (`components/login-again`), com o e-mail travado na conta aberta e só a senha para digitar. enquanto esse login está aberto, a tela de baixo continua montada mas fica escondida, como no aceite do termo, porque o computador pode ser de mais gente. o modal que estava aberto nela também não reage ao teclado enquanto ela está escondida, pelo login ou pelo termo: o `Esc` não fecha o que a pessoa nem vê e o `Tab` anda pelos controles da camada de cima (CT-39). ao entrar de novo, o envio vai outra vez com a sessão nova e a tela recebe a resposta de verdade, então uma escala ou anamnese pela metade não perde nada, e a tela só vê uma resposta demorada. como nos modais e no termo, o foco volta para onde estava quando o login abriu, como o botão que enviou, e não se perde no `body`; quando o termo abre logo depois de entrar, ele leva o foco e o aceite devolve para lá (CT-39). se o termo ficou pendente enquanto a sessão estava vencida, o aceite aparece no lugar da tela logo depois de entrar, como no login normal. "Sair" nesse login descarta o envio e vai para a tela de login. confirmar o e-mail novo em outra aba também encerra a sessão, e aí o e-mail travado é o antigo, que não entra mais: quando a api recusa o login, a tela diz para tocar em "Sair" e entrar com o e-mail novo. a conta desativada com a tela aberta não vê esse login (decisão de 13/11/2026): o `401` dela vem com `X-Account-Deactivated` e a mensagem do login, e o layout abre por cima o aviso *Acesso encerrado* com essa mensagem e só o botão "Sair", sem pedir a senha e sem prometer enviar o que estava na tela. esse "Sair" também chama `logout()`, porque o cookie dessa sessão ainda daria o motivo a quem abrisse o sistema depois no mesmo navegador; o "Sair" da sessão que só venceu não chama, porque o cookie de agora pode ser de quem entrou em outra aba. o login por cima que recebe o `403` da conta desativada (a sessão já tinha vencido) troca para o mesmo aviso. nada do que foi digitado é gravado no navegador, que pode ser de mais gente. se a api devolvesse outra conta, nada é reenviado, essa conta sai e a página recarrega no login. o cookie é um só para todas as abas, e outra aba pode ter saído e entrado em outra conta (o responsável com dois filhos, #152): por isso `request()` e `download()` mandam em cada envio o cabeçalho `X-Session-User` com o id de quem a tela mostra, e a api responde `401` quando o cookie é de outra conta. aí abre o mesmo login por cima, travado na conta da tela, e nada do que foi digitado vai para a ficha da outra (RF30). o login e o cadastro não mandam esse cabeçalho, porque são eles que trocam a conta, e o `logout()` também não. fora do layout (o link de senha nova aberto com alguém logado) o `401` recarrega a página no login com `?sessao=expirada&voltar=`, como antes, e na própria tela de login o `401` continua sendo senha errada. o paciente cujo aceite do termo de consentimento é de uma versão antiga, ou de outra faixa de idade (a data de nascimento cruzou os 18 anos), vê o termo no lugar de qualquer tela até aceitar, e um `403` com `X-Term-Pending` abre esse aceite por cima da tela aberta. o cadastro, esse aceite e o da pesquisa no perfil mandam a versão e o `textHash` que vieram com o texto, para a api guardar o hash do texto que a pessoa leu; quando ela recusa porque o termo mudou com a tela aberta, mesmo só no texto (um dado da clínica trocado), a tela busca o termo de novo, mostra o texto novo e desmarca o aceite (revisão das regras R21). salvar no perfil a data de nascimento pergunta de novo à api (`checkPendingTerm()`, que lê o `GET /auth/me`) e abre o termo na hora quando ela cruzou os 18 anos. pendente só pela faixa de idade (`termPendingByAge`), a tela do termo mostra a data salva e deixa corrigir a data errada sem aceitar; com a data certa o termo fecha e a tela de baixo monta de novo, para o perfil não voltar com a data errada no formulário. como nos modais, o termo que abre leva o foco para o aviso do topo dele, e ao fechar o foco volta para onde estava, como o *Salvar dados* do perfil; quando a tela de baixo montou de novo, ou o termo já estava aberto ao entrar, o foco vai para o começo do conteúdo (o `main`, que só fica focável dessa vez), e não se perde no `body` (CT-39). `setLoggedUser()` avisa o layout com o evento `logged-user-changed`, então o nome salvo no perfil aparece no menu na hora. como só a api apaga o cookie, `logout()` só esquece quem estava logado quando a api confirma a saída (um `401` também conta) e devolve se deu certo: se falhar, a tela avisa e a pessoa continua logada. a confirmação do e-mail novo (`pages/confirm-email`) também chama `logout()` depois que a api confirma a troca, quando há alguém logado naquele navegador: a api só encerra as sessões da conta do link, e a conta aberta pode ser outra (o responsável com dois filhos), que antes continuava com o cookie valendo depois de a tela ir para o login. a tela só vai para o login quando a saída dá certo; se falhar, ela diz que o e-mail foi confirmado e que não conseguiu sair daquela conta, e o botão vira **Sair da conta** (18/11/2026).

quando o servidor não responde, a tela mostra o aviso de sem conexão ("Não foi possível conectar ao sistema. Confira sua internet e tente de novo.", ou o texto próprio que a tela passa para `errorMessageOf` e `readRequestError`). isso vale para a falta de internet e também para a api parada atrás do proxy: o nginx e o vite respondem `502`, `503` ou `504` sem o json da api, e o `api.js` trata todo `5xx` sem esse json como sem conexão, inclusive no login, no login por cima e nos downloads. um `5xx` que vem com o json da api continua mostrando a mensagem dela. no registro de uma consulta nova e na prescrição, tentar de novo depois desse aviso não grava em dobro (decisão da dona do projeto, de novembro/2026): a resposta pode ter se perdido com o registro já gravado, então cada formulário sorteia uma chave quando abre (`newRequestKey()`, no `api.js`) e manda a mesma em todo envio dele, no cabeçalho `X-Request-Key` (o terceiro parâmetro de `apiService.post`). a api reconhece o envio repetido, com a mesma chave e o mesmo conteúdo, por 10 minutos, e devolve o registro que já gravou; a tela segue para *Consulta registrada* ou *Prescrição emitida* como se fosse a primeira resposta. o formulário aberto de novo sorteia outra chave, então a receita igual emitida de propósito continua saindo, e o que foi corrigido antes de tentar de novo é gravado como registro novo. ao abrir ou recarregar a página, só o `401` da api ao `GET /auth/me` quer dizer que ninguém está logado: com outra resposta, o `main.jsx` não manda para o login como se a pessoa tivesse saído da conta, porque o cookie pode continuar valendo. sem resposta, no lugar das rotas aparece *Sem conexão com o sistema*, com o mesmo aviso e o botão **Tentar de novo**, que recarrega a mesma tela. com outro erro que vem com o json da api, como o `500` dela ou o `429` do limite do nginx, aparece *Algo deu errado* com a mensagem desse json e o mesmo botão. o que não carregou não aparece como cartão vazio, como se não houvesse dado: no progresso, sem o catálogo ou sem o paciente aberto fica só o aviso de sem conexão, e o mesmo vale para a escolha do paciente sem a lista de pacientes. só o `403` e o `404` do paciente mostram o acesso negado com o link para a lista. na tela de um paciente, a lista de pacientes serve só para trocar de paciente, então, se só ela falhar, o aviso aparece junto do gráfico, que continua. o cartão dos comentários que não carregaram diz isso, em vez de *Nenhum comentário* (13/11/2026). as gotas do dia que não carregaram também dizem isso no cartão do gráfico, que continua com o item, sem a legenda e o eixo das gotas (14/11/2026). com a internet lenta, enquanto o catálogo e os comentários do período ainda estão chegando, o gráfico e o cartão dos comentários ficam no esqueleto, sem o número do lado do título, em vez de dizer *Nenhum registro preenchido* ou *Nenhum comentário* antes da hora (CT-40). ao trocar o período, o cartão *Consultas no período* sai da tela até chegarem as consultas do período novo, em vez de continuar com a lista e o número do anterior, e as marcas das consultas esperam o gráfico do período novo. as gotas do dia também: até chegarem as do período novo, o gráfico fica sem gota nenhuma, e as do anterior não esticam o eixo. no gráfico, o eixo vai pela data, a linha se interrompe onde passou mais tempo do que a frequência da escala sem resposta, que vem no catálogo de atributos (`frequencyDays`), e liga uma resposta à outra na escala sem frequência fixa, como a Hamilton, o Pittsburgh e o MEEM. a consulta entre a primeira e a última resposta vira marca no dia dela, mesmo sem preenchimento nesse dia, e as datas embaixo do eixo ficam perto de posições espalhadas por igual, sem um buraco antes da última (decisão de 14/11/2026, revisão das regras R3). duas consultas no mesmo dia viram uma marca só, que sai como *consulta + receita* quando qualquer uma delas teve receita (14/11/2026). o eixo vai da primeira à última resposta, que sempre têm a data embaixo: a consulta de antes da primeira ou de depois da última não vira marca e fica só no cartão *Consultas no período*, e o ano nas datas do eixo segue só as respostas (`components/line-chart`).

embaixo do gráfico do progresso, o botão *Ver como tabela* mostra os mesmos pontos numa tabela de verdade, com legenda (`caption`), títulos de coluna (`th scope="col"`) e a data como título da linha, para quem usa leitor de tela no celular, onde as setas do gráfico não existem, e para quem quer o número exato de cada dia. cada linha é um ponto: dois MEEM no mesmo dia, um em cada consulta, são dois pontos no gráfico e duas linhas na tabela, na ordem em que a api manda, e a gota do dia vai só na primeira linha daquela data. a tabela vem fechada e é montada com as linhas que o gráfico já recebeu, sem pedido novo à api: o que a api não manda, como a resposta anulada e o MEEM para o paciente, também não aparece nela. o texto de cada dia é o mesmo da dica do ponto (`scoreText` e `doseText`, em `utils/progress-reading.js`): o escore com a faixa do lado, *em branco* no item ou na gota que ficou em branco, nunca zero, e a dose parcial dizendo qual dose faltou. a coluna *Gotas no dia* só existe enquanto o gráfico mostra as gotas. a tabela fica como a pessoa deixou ao trocar o período, a escala e o item, e volta fechada ao trocar de paciente. ela existe só na tela de progresso (20/11/2026).

## datas

a api trabalha no horário de Brasília (`America/Sao_Paulo`) e as telas também. o hoje e o agora saem de `utils/date-format.js`, que usa o fuso de Brasília mesmo com o navegador em outro fuso: `toIsoDate(new Date())` é o dia de hoje em Brasília, e `isInTheFuture`, `hasEnded` e `minutesUntil` comparam o horário da consulta com o agora de Brasília. os horários aparecem como a api manda, e sempre que o fuso do navegador não é `America/Sao_Paulo`, mesmo outro de UTC-3 como `America/Fortaleza`, vai "(horário de Brasília)" do lado: `brasiliaTimeNote()` depois do horário nas telas de consultas e do painel do paciente, e `withBrasiliaTimeNote(texto)` nos avisos que já vêm com o horário no texto, no painel do paciente e na página de avisos, que o prescritor também vê. um dia montado pela tela (`addDays`, `mondayOf`, `new Date("2026-10-16T00:00:00")`) fica no começo do dia local, que onde o horário de verão pula a meia-noite é 1h. os testes contam o hoje do mesmo jeito, com `toIsoDate` e `addDays`, e nunca com `new Date().getDay()` ou `getDate()`, que dão o dia do fuso da máquina: o CI roda em UTC, e às 23h43 de sábado em Brasília ele já está no domingo. o teste da grade do diário em `pages/escala` fixa esse momento com `vi.setSystemTime` e `TZ=UTC`. o relógio fixado nos testes é um instante com o fuso escrito, como `new Date("2026-10-16T10:00:00-03:00")`, e nunca `new Date(2026, 9, 16, 10, 0)`, que é a hora do fuso da máquina: em Tóquio essas 10h ainda são 22h do dia anterior em Brasília, e a idade de `utils/guardian.js` mudava (o teste dela roda também com `TZ=Asia/Tokyo`).

## agenda do prescritor

na agenda do prescritor (`pages/agendamento-consulta-prescritor`), cada consulta da semana mostra só os botões que valem para a situação dela. a consulta marcada tem *Remarcar* até começar e *Registrar atendimento* depois, *Marcar falta* depois que o horário termina e *Cancelar* só até esse fim, que é o início mais a duração (`hasEnded`). depois do fim a api recusa o cancelamento, porque o paciente recebia *Consulta cancelada* de uma consulta que já tinha passado, e sobram *Registrar atendimento* e *Marcar falta* (decisão de 17/11/2026).

a grade da semana esconde os pedidos recusados e as consultas canceladas, que não têm botão nenhum: o paciente que pedia de novo deixava o pedido recusado ao lado do novo e a grade enchia. o botão *Mostrar recusados e cancelados*, com a quantidade da semana entre parênteses quando há algum, mostra os dois de volta no lugar deles, e *Esconder recusados e cancelados* tira de novo. o texto do botão muda junto, e a escolha vale enquanto a tela está aberta, também ao trocar de semana. o dia que só tinha recusados ou cancelados mostra *Nenhuma consulta.*, como o dia vazio. o resto não muda: a marcada, a em andamento, a concluída, a falta e a anulada aparecem como antes, e os horários livres, os *Pedidos aguardando resposta* e as telas do paciente ficam iguais (decisão de 17/11/2026).

o dia sem consulta é uma linha curta: o nome do dia e *Nenhuma consulta.* lado a lado, numa caixa baixa que não estica até a altura do dia cheio ao lado (`.dayWithoutAppointments`, com `align-self: start`); se os dois não cabem na mesma linha, o aviso desce. antes o dia vazio ocupava a mesma caixa do dia cheio e empurrava as consultas para longe. o dia de hoje continua com o traço verde e o selo *hoje*, com ou sem consulta. no celular, onde os dias ficam um embaixo do outro, a agenda abre rolada até o dia de hoje (`isPhoneWidth`, em `utils/phone-width.js`, e `scrollIntoView`), uma vez só, quando a tela carrega: trocar de semana, voltar para *Esta semana* e as ações da agenda não puxam a tela de novo, o foco do teclado não muda de lugar e os *Pedidos aguardando resposta* continuam logo acima, rolando para cima. no computador a agenda abre no alto, como antes (decisão da dona do projeto, novembro de 2026).

## painel do prescritor

o cartão *Pacientes ativos* do Início (`pages/dashboard-prescritor`) conta todo paciente fora do arquivo, e os *Indicadores* contam só quem está fora do arquivo e com a conta ativa. quando a administração desativa a conta de um paciente, os dois números ficam diferentes com o mesmo nome. por isso o cartão mostra, embaixo do nome, a nota *N com a conta desativada* (`deactivatedAccountPatients` do painel), só quando há algum: o número do cartão menos o da nota é o dos Indicadores. o texto dos Indicadores não mudou (decisão da dona do projeto, novembro de 2026).

## escalas

a tela de escala (`pages/escala`) monta o formulário com a definição que vem da api. no diário a grade mostra os dias da tarefa aberta (no celular ela rola de lado e anda sozinha até o dia escolhido, sem mexer na rolagem da página) e, antes deles, os da semana que fechou ontem, até o fim do dia: a tela acha essa semana em `GET /patients/{id}/scales` (a tarefa que não está pendente e acaba ontem), avisa que os dias dela contam como preenchidos com atraso, escolher um dia dela deixa a mesma grade e, sem período aberto, abre no último dia dela (decisão de 14/11/2026, revisão das regras R6). sem período aberto, a grade continua sendo a semana de hoje até hoje, como era antes, e a semana que fechou ontem só entra antes dela: hoje nunca sai da grade, e escolher hoje deixa a mesma grade. o que a pessoa mexe fica guardado por dia (`editsByDay`) até salvar: o dia com rascunho aparece como *não salvo* na grade, **Salvar respostas** envia cada dia editado num `POST` próprio, em ordem de data, e o painel de pronto diz quantos dias foram salvos. o dia que a api recusa continua como rascunho *não salvo* e o erro dele aparece na tela. se a rede cai no meio do salvar e a recarga depois dele também falha, a tela continua como estava, com a grade, os rascunhos e o erro de cada dia, e junta o aviso *Não foi possível atualizar a tela agora. As respostas salvas continuam salvas.*; só a primeira carga que falha troca a tela pelo aviso de erro. o erro de campo que a api manda, como o horário de levantar igual ao de dormir no diário do sono, aparece também no próprio item, ligado ao campo por `aria-describedby`, até o próximo envio. a recusa de campo que não é de nenhum item, como salvar o TEA, o acompanhamento semanal ou o diário do sono sem responder nada (*Responda ao menos um item da escala*), vai com o motivo para o aviso, no lugar de *Confira os campos destacados*, porque não há item para marcar. sair da tela com rascunho pergunta antes, com o mesmo modal de confirmação da anamnese: o `useBlocker` do react router segura qualquer saída, seja o **Voltar** do formulário, a seta e o **Voltar** do layout ou o menu. quando a escala é a primeira tela da aba (aberta pelo endereço, por favorito ou por link colado, mesmo depois de recarregar ou de salvar com outra data), não há tela do app para onde voltar, então o **Voltar** do formulário leva à central de escalas, e o modal pergunta do mesmo jeito. já a escala aberta pelo app e depois recarregada ainda tem a tela de antes na aba, e o **Voltar** volta para ela: com rascunho, quem pergunta é o modal ou, se o navegador carregar aquela tela de novo, o próprio navegador. recarregar, fechar a aba ou sair do app pelo navegador não passam pelo router: com rascunho, o próprio navegador pergunta antes (`beforeunload`, em `utils/leave-warning.js`). trocar só a data na url continua na tela e não pergunta, e sair da conta também não, porque a sessão já acabou.

o formulário de qualquer escala (`components/scale-form`) começa com um contador preso no alto, como *7 de 19 respondidas*, que acompanha a rolagem: no computador ele para no alto da janela e, no celular, logo abaixo do cabeçalho, sempre embaixo das barras do layout. ele conta só o que a pessoa respondeu, e o item limpo com **Limpar resposta** deixa de contar. o total são todas as perguntas do formulário, inclusive as que podem ficar em branco, como as *Observações* e o texto livre das outras razões do Pittsburgh: todas estão na ficha em papel de `docs/scales`, então a escala trata essas perguntas como parte do formulário, e o total bate com o número de perguntas na tela. só os valores que o sistema calcula (os tempos do diário do sono) ficam fora, porque não são perguntas. o texto do contador é um `role="status"`, que o leitor de tela lê sem interromper quando a conta muda; no texto livre ela só muda no primeiro caractere, e não a cada letra. o contador tem `data-top-bar`, e o campo que recebe o foco atrás dele desce só o bastante para aparecer inteiro (`utils/focus-above-bars.js`). salvar com item obrigatório em branco continua sem enviar e listando o que falta perto do botão, e agora também leva o foco e a rolagem ao primeiro item que falta: o item marcado fica com `aria-invalid`, e a tela usa o mesmo `useFocusFirstError` dos outros formulários, que também leva o foco ao campo que a api recusou, como o horário de levantar do diário do sono. o Mini-Exame do prescritor tem o mesmo contador e o mesmo foco no primeiro item que falta (17/11/2026).

no celular, abaixo de 768 px (`utils/phone-width.js`, que lê com `matchMedia` a mesma quebra do css), a escala do paciente mostra uma pergunta por tela, com **Anterior** e **Próxima** na barra de ações, e o contador diz também em que pergunta a pessoa está (*Pergunta 3 de 19 · 7 de 19 respondidas*). o valor que o sistema calcula aparece na tela da pergunta de antes dele, como o tempo na cama junto do horário de levantar (`components/scale-form/scale-steps.js`). esse valor é sempre a conta das respostas que estão na tela: ao mexer numa resposta de um dia já salvo, o valor calculado antigo sai da tela e volta o texto *o sistema calcula quando você salvar*, como num dia novo, até a api devolver a conta refeita; a tela não refaz a conta (20/11/2026). **Próxima** nunca trava: dá para pular uma pergunta (RN10), e o **Salvar respostas**, que só aparece na última, lista o que falta como antes e volta para a primeira pergunta que falta, com o foco nela. na primeira pergunta, o botão da esquerda é o **Voltar** de sempre. a cada tela o foco vai para a pergunta nova (o grupo das opções ou o próprio campo; na resposta que o prescritor já analisou, travada, o campo não recebe foco e ele vai para o título da pergunta) e o contador anuncia a pergunta. depois do foco a tela rola até o cartão inteiro da pergunta, e não só até o campo: numa janela baixa (320x256) o navegador parava no campo digitado e o texto da pergunta ficava acima da janela. se o cartão for mais alto que a janela, ele sobe até o alto dela, para o nome da pergunta aparecer, e o campo com foco puxa de volta só o que falta para continuar inteiro na vista; o cartão que ficaria atrás do contador preso desce até sair de baixo dele. só quando o nome, o texto de apoio e o campo juntos não cabem na janela (as *Observações* do TEA e da dor em 320x256, que somam 280 px) o nome fica acima dela e o campo com foco ganha (21/11/2026). no diário, onde o campo da pergunta é o único do formulário, o enter num campo de uma pergunta do meio só passa para a próxima, sem salvar o dia pela metade; nas outras escalas a data fica no formulário junto com o campo e, sem o botão de salvar na tela, o navegador não envia nada com o enter, então numa pergunta do meio o enter não faz nada. no diário, cada dia da grade é um formulário: escolher outro dia abre a primeira pergunta dele, e o salvar de vários dias continua igual. a pergunta da tela fica guardada também no computador, onde ela segue a pergunta que recebe o foco e a que foi respondida (o Safari não dá foco à opção clicada ou tocada), então girar o aparelho ou esticar a janela mantém as respostas e a pergunta, e ao passar para o computador a página rola até ela. no computador essa pergunta só fica guardada, sem desenhar a página de novo a cada foco: o React reescreve as opções a cada desenho, e com isso o Chrome parava duas vezes no tab de cada pergunta sem resposta. o aviso de sair sem salvar, o erro de cada dia e o aviso de rede caída continuam iguais. para ficar simples, o voltar do navegador não volta pergunta por pergunta: ele sai da tela, como antes, e com rascunho o modal pergunta. a partir de 768 px a escala continua toda numa página, e o Mini-Exame do prescritor nunca entra nesse modo (17/11/2026).

cada opção de escolha é um cartão da largura toda, com pelo menos 44 px de altura (48 px no celular), e o *Sim* e o *Não* ficam em dois cartões lado a lado. a opção escolhida não depende só da cor: a bolinha ganha um check e a borda fica dobrada, além do fundo verde. o check só existe na escolhida e a borda dobrada é borda de verdade, e não sombra, porque o alto contraste do Windows troca as cores do site pelas do sistema e tira as sombras; lá a nota e a opção escolhidas usam a cor de destaque do sistema (`forced-colors`). o radio de verdade continua no lugar, invisível, então o teclado anda pelas opções com as setas, o anel de foco aparece no cartão e o leitor de tela lê a opção, como no `ChoiceCard`. a régua de notas continua régua, com o mesmo desenho e as faixas da dor (RF25): no celular cada nota tem pelo menos 44 px de largura e 48 px de altura, a escolhida fica cheia e com um anel por dentro, e o que não cabe desce para a linha de baixo, sem rolar a página de lado em 375 px. vale também para o Mini-Exame (17/11/2026). os cartões de uma mesma pergunta têm todos a altura do mais alto, para a opção de texto comprido não parecer mais importante nem ser mais fácil de acertar: as opções de cada pergunta ficam numa grade só dela (`grid-auto-rows: 1fr`), então a altura nunca passa de uma pergunta para outra, e o cartão que se vê enche a área de toque. o *Sim* e o *Não* continuam lado a lado, em duas colunas iguais. o texto de apoio embaixo da pergunta, que em várias escalas é texto do próprio instrumento, tem o tamanho do texto da página, 16 px, e não mais 14 px. é só css: a ordem e o texto das opções não mudam. medido no Chrome sem janela em 375 e em 320 px, nos dois temas: na pergunta 10 do Pittsburgh os quatro cartões têm 74 px (antes, dois de 50 e dois de 74), e no TEA e no Mini-Exame todos têm 50 px (20/11/2026).

na régua com as faixas da dor, no celular (abaixo de 768 px), as onze notas de 0 a 10 têm todas o mesmo tamanho, 44 px de largura por 48 px de altura. antes cada faixa caía na sua linha e esticava até a borda, então em 375 px as notas de 0 a 2 e de 8 a 10 tinham 92 px de largura e as de 3 a 7 tinham 52 px, e a nota mais larga era mais fácil de acertar. agora a faixa fica do tamanho das notas dela (`max-width: max-content` e coluna fixa de 44 px), as linhas por faixa continuam como eram, com o nome de cada faixa em cima das notas dela, e o espaço entre as notas caiu de 8 para 4 px para a faixa de cinco notas caber também em 320 px, onde antes ela passava 14 px da folga do cartão. medido no Chrome sem janela em 320, 360, 375, 414, 600 e 700 px, nos dois temas em 320 e 375 px: as onze caixas têm 44 por 48 px e a página não rola de lado. a partir de 768 px a régua continua como era (20/11/2026).

onde o próprio instrumento junta vários itens embaixo de uma pergunta, a tela mostra essa pergunta uma vez, como título em cima deles, com um fio verde do lado: a 5 do Pittsburgh (*Durante o último mês, com que frequência você teve dificuldade para dormir porque você:*, os itens de a até j, com as outras razões), a da dor (*Durante a última semana com que frequência a dor te atrapalhou:*, desde 20/11/2026) e a do TEA (*Durante a última semana com que frequência esses comportamentos ocorreram:*). o texto vem do papel de `docs/scales` e chega no campo `section` de cada item da definição; o escore não usa esse campo. as opções e a ordem dos itens continuam exatamente como estão no catálogo. no celular, a tela de cada item da parte traz o título em cima, para a pergunta não perder o sentido. a ficha de acompanhamento semanal, o diário do sono, a Hamilton e o MEEM não juntam itens no papel e ficam sem título de parte (17/11/2026).

o paciente lê a pergunta inteira do papel. quando o item da definição traz `question` (no Pittsburgh, na dor e no TEA), o formulário mostra essa frase no lugar do `label`, do mesmo tamanho e peso, e o `label` vira o nome curto do item: ele não aparece junto da pergunta e fica só na lista *Falta preencher*, no *Limpar resposta de…* para o leitor de tela, na leitura da resposta (`pages/resposta-escala`) e, vindo da api, no gráfico e nos CSV. nas perguntas de 1 a 4 do Pittsburgh a ajuda embaixo da pergunta é o nome do campo de resposta, que o papel também traz (*Hora usual de deitar:*). a frase que o papel põe antes de uma pergunta chega em `intro` e aparece uma vez em cima dela (o *Para cada uma das questões restantes, marque a melhor (uma) resposta* do Pittsburgh, antes da pergunta 5); no celular ela aparece só na tela do item que a traz, e o leitor de tela lê junto com a parte. a mesma frase nunca aparece duas vezes na tela: a letra j do Pittsburgh fica embaixo do título da pergunta 5 com a frase dela. a comparação de cada item com o papel está em [`docs/qa/migracao-das-escalas.md`](../docs/qa/migracao-das-escalas.md) (20/11/2026).

depois de salvar tudo o que foi mexido, o formulário dá lugar a um painel de pronto, como no registro da consulta e no MEEM: *Pronto, obrigado!* (ou *Respostas de 3 dias salvas*, quando o diário salvou vários dias), o resultado que a escala já mostrava (*Resultado:*, com o texto da api), o que foi salvo (o dia, os dias, o período ou a data da avaliação) e o que vem depois, só quando a tela sabe: no diário com período aberto, *Amanhã tem mais um dia para preencher.*, ou *Hoje é o último dia deste período.* quando hoje é o último dia dele; sem isso, a frase neutra *Quando a clínica enviar a próxima, ela aparece em Escalas.*, sem inventar data. o foco vai para o painel (`role="status"`), porque o botão que salvou saiu com o formulário. os botões são **Voltar para Escalas**, **Ir para o início** e **Ver respostas salvas**, que traz o formulário de volta, já na correção da resposta salva, para a pessoa poder corrigir na hora como antes. esse botão some junto com o painel, então o foco vai para a primeira pergunta, e não cai no começo da página: no celular, como na troca de tela; no computador, no título da pergunta de opções ou no próprio campo, porque o grupo com `tabIndex` pegaria o foco no clique do mouse antes da opção; no diário a grade continua em cima do painel, e escolher um dia também volta para o formulário. quando algum dia é recusado, o formulário fica, com o erro do dia e o aviso de quantos foram salvos, como antes, e o aviso de que a tela não atualizou depois de salvar aparece em cima do painel. o Mini-Exame continua com o próprio resultado e não tem esse painel (17/11/2026).

o botão **Responder** dos cartões de *Esperando resposta*, na central de escalas (`pages/escala-clinica-paciente`) e no painel do paciente (`pages/dashboard-paciente`), segue o `answerPath` que a api manda, e não o `path` da escala: na tarefa reaberta pela anulação, quando hoje é de outra pendente da mesma escala ou fica fora dela, ele vem com a data dela (`?data=`), como o aviso da anulação, então a resposta cai na tarefa reaberta em vez de fechar a rodada nova da mesma escala, e no diário a grade abre na semana reaberta, no dia anulado. o `path` continua só o da escala, porque a tela de escala acha a pendente por ele (14/11/2026).

a anamnese (`pages/anamnese`) segue a mesma regra: com algo digitado, ou mudado na correção, o **Cancelar** do formulário, a seta e o **Voltar** do layout e o menu perguntam antes com o modal *Sair sem enviar* (*Sair sem salvar* na correção), e recarregar ou fechar a aba faz o navegador perguntar. a ficha sem nada digitado e a ficha enviada saem sem perguntar. na ficha para leitura (`components/anamnesis-view`), que o histórico e a impressão usam, o peso e a altura aparecem com vírgula decimal (`68,5`), como o peso da consulta, e a resposta escrita de outro jeito aparece como veio (13/11/2026). no histórico do paciente (`pages/historico-clinico-paciente`) o **Preencher anamnese** aparece enquanto não há ficha válida: com a lista vazia e também quando todas as fichas foram anuladas, acima do cartão anulado, porque a anulada não conta. o paciente arquivado não vê o botão (18/11/2026).

o texto livre do paciente vem com o aviso fixo *Isto não é atendimento de urgência. Se algo piorou, fale com a clínica ou procure um serviço de saúde.* (`components/urgency-notice`, decisão de 14/11/2026, revisão das regras R1): embaixo do *Motivo da consulta* do pedido, embaixo de cada campo de texto das escalas na tela do paciente (o `ScaleForm` recebe `showsUrgencyNotice`, que o Mini-Exame do prescritor não passa) e no alto de cada parte da anamnese (*Sobre você*, *Histórico de saúde*, *Hábitos*, *Como você está hoje* e *Sobre o tratamento*), que é quase toda de texto livre. o aviso fica ligado ao campo pelo `aria-describedby` (no `TextAreaField`, pelo `noticeId`; na anamnese, cada campo de texto longo fica ligado ao aviso da parte dele), e o leitor de tela lê junto com o campo

o registro da consulta (`pages/consultation-record`), a prescrição (`pages/prescription-form`) e o Mini-Exame (`pages/mini-exame`) do prescritor seguem a mesma regra desde 13/11/2026: com algo digitado ou marcado, ou mudado no registro de uma consulta já salva, o **Voltar** do formulário, a seta e o **Voltar** do layout e o menu perguntam antes com o modal *Sair sem salvar*, e recarregar ou fechar a aba faz o navegador perguntar. enquanto o envio está em andamento, depois de salvar e sem nada digitado a saída não pergunta. antes as três telas saíam caladas e o que foi digitado se perdia. o envio parado atrás do login por cima não é envio em andamento (decisão da dona do projeto, de novembro/2026): a sessão venceu, nada foi gravado ainda, e as três telas perguntam antes de sair nesse momento, como a anamnese e as escalas já faziam. recarregar ou fechar a aba faz o navegador perguntar, e o voltar do navegador não sai da tela, que continua embaixo do login; a pergunta *Sair sem salvar* fica escondida junto com ela e é esquecida quando a pessoa entra de novo, porque aí o envio segue e a tela mostra *Consulta registrada*, *Prescrição emitida* ou o resultado do exame (`useForgetBlockedExit`, em `utils/leave-warning.js`). antes o voltar saía da tela, o envio guardado era gravado depois do login sem nenhuma tela mostrar, e o prescritor podia emitir a receita de novo. o `api.js` diz se há envio esperando o login (`hasSendWaitingLogin()`) e avisa com o evento `waiting-login-changed` quando isso muda; as telas leem pelo `useSendWaitingLogin()`. o **Sair** do login por cima continua indo para a tela de entrada sem perguntar.

a consulta e a prescrição anuladas chegam ao paciente sem o conteúdo (`contentHidden`), e o cartão delas (`components/consultation-card` e `components/prescription-card`) mostra só a data, a marca *Anulada* e a faixa da anulação, no histórico, em Minhas prescrições e na impressão. o modal de anulação recebe `patientNote`, que diz o que o paciente vê do registro anulado: na consulta e na prescrição, só a data, a marca e o motivo, com o pedido de não escrever no motivo o nome nem dados de outra pessoa; na anamnese e na escala, o registro marcado como anulado; no MEEM, que o paciente não vê, nada (decisão de 14/11/2026, revisão das regras R7).

o prontuário do paciente arquivado não recebe consulta, prescrição nem Mini-Exame novos, e a api recusa (decisão de 17/11/2026). as telas do prescritor não oferecem o que ela recusa: o histórico do arquivado fica sem *Nova consulta*, *Emitir prescrição*, *Mini-exame* e *Desfazer falta e registrar atendimento*, e mostra uma linha dizendo que o paciente está arquivado e que é reativado na aba Arquivados da lista de pacientes; *Editar registro* da consulta concluída e *Anular* continuam. na agenda, a consulta dele que já começou mostra *Paciente arquivado: reative antes de registrar o atendimento* no lugar do botão, e no painel a consulta de hoje dele tem *Ver histórico* no lugar de *Registrar*. depois de corrigir o registro de uma consulta concluída dele, a tela não oferece *Emitir prescrição* nem *Aplicar mini-exame*. as telas da consulta, da prescrição e do Mini-Exame, abertas pelo endereço, mostram a mesma linha no lugar do formulário (a consulta já concluída continua abrindo para correção, e o exame já aplicado abre no resultado). os textos ficam em `utils/archived-patient.js`.

em *Enviar escalas* (`pages/selecao-escalas`), o cartão da *Avaliação inicial* de um paciente arquivado já vem bloqueado, sem marcar, com o motivo no lugar da descrição: *Paciente arquivado não preenche a avaliação inicial. Reative o paciente, na aba Arquivados da lista de pacientes, antes de enviar.* (`ARCHIVED_INITIAL_ASSESSMENT_NOTICE`, em `utils/archived-patient.js`). antes o cartão se marcava, a api recusava no envio e a recusa parava as outras escalas marcadas, que só iam num segundo clique. as outras escalas do arquivado continuam indo num clique só, e o paciente fora do arquivo marca a avaliação inicial como qualquer escala (decisão da dona do projeto, novembro de 2026).

a receita vigente do paciente arquivado chega com `followUpEndedAt`. o cartão da prescrição mostra *Última prescrição* no lugar de *Vigente*, sem o destaque de receita em uso, e *Acompanhamento encerrado em* com a data. em Minhas prescrições a seção *Vigente* e na impressão a seção *Prescrição em uso* viram *Última prescrição, acompanhamento encerrado em* com a data (`lastPrescriptionTitle`, em `utils/prescription-labels.js`), e no painel do paciente o cartão *Prescrição de agora* vira *Última prescrição*. o texto do topo de Minhas prescrições, que explica a vigente, vira *Seu acompanhamento foi encerrado em* com a data e *A última prescrição fica guardada abaixo.*; o CSV continua com a situação gravada. no histórico do prescritor, o modal de anular essa receita não fala em uso: avisa que ela é a última, que o paciente fica sem prescrição, também se for reativado, e que a anterior não volta a valer (decisão de 14/11/2026, revisão das regras R2).

no registro da consulta, os blocos de texto *Queixa e exame*, *Avaliação* e *Conduta* dizem que o paciente lê aquele texto em Meu histórico clínico, e o responsável também quando o paciente é menor de idade. a frase é a `description` do `FormSection`, ligada ao bloco por `aria-describedby`, e o leitor de tela lê junto com o título (decisão de 14/11/2026, revisão das regras R8).

no plano de dose da prescrição, a semana vazia no meio é recusada antes de enviar, com "Preencha ou tire a semana N" na linha dela, e as vazias do fim continuam ficando de fora. o erro de uma linha é guardado pela posição dela, então **Tirar** uma semana ou um canabinoide limpa os erros daquela lista, para o erro da linha tirada não passar para a que subiu, e o aviso de cima some quando não sobra erro nenhum (18/11/2026). o formulário e o cartão da prescrição (`components/prescription-card`) dizem "Semana 1 = primeira semana de uso" (decisão de 14/11/2026, revisão das regras R23).

o paciente não vê o Mini-Exame do Estado Mental (decisão de 13/11/2026): a api deixa o exame de fora das listas dele e recusa com 403 o que ele pede direto, então as telas do paciente (central de escalas, histórico, resposta, progresso, impressão e painel) só mostram o que vem e nenhuma fala do exame. a tela de escala perdeu o aviso que só existia para o paciente que abria o endereço do mini-exame. o progresso só pede a série de um atributo que veio no catálogo, então o atributo do MEEM num link antigo nem chega na api e a tela abre no primeiro atributo do paciente. as telas do prescritor (mini-exame, histórico, progresso, exportação e impressão) continuam com o exame.

na resposta aberta para leitura (`pages/resposta-escala`), as horas, que aceitam meia hora (*Horas de sono por noite* no PSQI e *Tempo fora de casa* no diário), aparecem com vírgula decimal e sem zero à toa, `6,5` e `7`, como no `scales.csv` (`formatAnswer` em `utils/scale-answers.js`, 18/11/2026).

a correção do paciente guarda a versão anterior (decisão de 14/11/2026, revisão das regras R4), e a api só manda essas versões para o prescritor. na lista *Respondidas* do histórico (`components/scale-summary`), a resposta corrigida mostra "corrigida em dd/mm/aaaa · antes:" com o resultado de antes da última correção, e a tabela *Escalas respondidas* da impressão (`pages/impressao`) mostra o mesmo embaixo do resultado. a resposta aberta para leitura (`pages/resposta-escala`) avisa quando foi corrigida e termina com o cartão *Antes das correções*, uma parte por correção, da mais nova para a mais velha, só com o resultado, o período e os itens que mudaram naquela correção. a ficha de anamnese (`components/anamnesis-view`, no histórico e na impressão) ganha o selo *Corrigida em* e, embaixo, o que estava antes em cada correção, só nos campos que mudaram, com "em branco" para o campo que estava vazio. as telas do paciente recebem a lista vazia e ficam como antes.

o acompanhamento automático (`pages/acompanhamento-protocolo`) lê o último acompanhamento do paciente (`/treatment-protocol/last`), em andamento ou encerrado, e preenche com ele o formulário: escalas, frequências, duração e horários do sono. os horários só aparecem com o Diário do sono marcado, e sem ele vão nulos no envio, para não ficar valendo para o paciente uma programação que a prescritora não vê no formulário (19/11/2026); a api também não guarda os horários que chegarem sem o diário (20/11/2026). o quadro *Em andamento* só aparece para o que está valendo. o botão **Encerrar acompanhamento** dele abre uma confirmação que diz o que acontece: o sistema para de enviar as escalas e fecha na hora as do acompanhamento que ainda esperavam resposta, e o paciente não é mais cobrado por elas (decisão da dona do projeto, novembro de 2026; antes a janela só falava dos envios, e as escalas já enviadas seguiam até o prazo). nos últimos 7 dias dele, quando a prescritora recebe o aviso, o formulário aparece embaixo do quadro com a data de início em hoje, no máximo hoje, e o botão vira **Renovar acompanhamento**; depois de encerrado, o formulário também volta preenchido. assim a renovação sai com um clique, em vez de montar tudo de novo de memória (revisão das regras R5, 14/11/2026).

o MEEM de quem tinha menos de 18 anos no dia da consulta vem da api com "Instrumento não validado para a idade" no lugar da faixa e sem corte. o resultado do exame, o ponto do gráfico e a impressão mostram esse texto ao lado do escore, e o progresso não conta esse exame como sem escolaridade (`utils/progress-reading.js`, decisão de 14/11/2026, revisão das regras R14).

## padrão de código

vale para todo código novo ou reescrito:

- arquivos e pastas em kebab-case, componentes em PascalCase, variáveis e funções em camelCase, tudo em inglês
- css modules (`nome.module.css`) em componente novo, para o estilo de uma tela não vazar para outra
- comentários curtos, em minúsculas, sem acento e sem pontuação
- texto que aparece na tela em português

## situação das telas

todas as telas seguem o padrão novo, cada uma com o seu css module. o css global que sobrou fica em `src/styles`: cores, fontes, botões, campos, avisos e os tokens de espaço e tamanho.
