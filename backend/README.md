# backend do 2ag

api em java que guarda os dados clínicos e aplica as regras de acesso. o que o sistema precisa fazer está em [`docs/requisitos-v2.md`](../docs/requisitos-v2.md).

## tecnologias

- java 17 e spring boot 4.1
- spring data jpa com hibernate, e **flyway** para o esquema do banco
- spring security com sessão em cookie `httpOnly` assinada com jwt (jjwt 0.13). o json de dentro do token é escrito e lido pelo jackson 3 do próprio spring boot (`security/JwtJsonSerializer`, registrado em `META-INF/services`), então o jackson 2 não entra no classpath
- postgresql em produção e h2 em memória nos testes
- maven, pelo wrapper `mvnw` que já vem no repositório

## rodando

```bash
cd backend/doisag
export DATABASE_PASSWORD='a_senha_do_banco'
export JWT_SECRET="$(openssl rand -base64 48)"
export SESSION_SECURE_COOKIE=false
export PUBLIC_URL=http://localhost:5173
export SEED_DADOS_TESTE=true
export SPRING_PROFILES_ACTIVE=dev
./mvnw spring-boot:run
```

o perfil `dev` deixa a api subir sem `CLINIC_NAME`, `CLINIC_CNPJ` e `CLINIC_DPO_CONTACT`, com os colchetes no termo. fora dos perfis `dev` e `test` ela não sobe sem as três (revisão das regras R21).

a api responde em `http://localhost:8080/api`. toda rota fica embaixo de `/api` para o front e a api dividirem a mesma origem, sem cors.

o `SESSION_SECURE_COOKIE=false` é só porque aqui o front roda em http, no `npm run dev`. no servidor e no compose, que rodam em https, ele fica `true`.

para mexer só nas telas, sem instalar postgres, a api sobe com o h2 em memória dos testes. os dados somem quando ela para:

```bash
./mvnw spring-boot:test-run "-Dspring-boot.run.arguments=--spring.profiles.active=test --api.seed.enabled=true --api.session.secure-cookie=false"
```

nesse modo a conexão com o banco não tem prazo (`spring.datasource.hikari.max-lifetime: 0` no `application-test.yml`). o h2 2.4 não consegue mais avaliar as checagens (`check`) de uma tabela depois que fecha a conexão que criou essa tabela, a das migrações, e passa a recusar toda gravação nela ("Check constraint invalid"), mesmo a que respeita a checagem. com o prazo padrão do pool, de 30 minutos, a api parava de gravar tudo o que entra na trilha meia hora depois de subir, sempre com `409` "Este registro já existe ou está em uso".

## documentação da api

a documentação gerada do código fica em `/api/swagger-ui/index.html` no endereço do front (`http://localhost:5173/api/swagger-ui/index.html` com o `npm run dev`; o json cru em `/api/v3/api-docs`), com o corpo e a resposta de cada rota tirados dos dtos e, em cada rota, quem pode usar, lido das regras de acesso do código. ela só abre para quem está logado: entre no sistema e abra o endereço. pelo endereço da api direto (`:8080`) a página abre, mas o *try it out* do que grava recebe 403, porque a origem não é o `PUBLIC_URL`.

ela só existe rodando com o perfil `docs` do maven e com `--api.docs.enabled=true` (ou `export API_DOCS=true`):

```bash
./mvnw spring-boot:test-run -Pdocs "-Dspring-boot.run.arguments=--spring.profiles.active=test --api.seed.enabled=true --api.session.secure-cookie=false --api.docs.enabled=true"
```

o perfil existe de propósito: o springdoc traz o jackson 2 de volta pelo swagger-core, e a imagem de produção (`mvn package` sem perfil) segue só com o jackson 3. a configuração dele mora em `src/docs/java`, que só compila com o perfil, e o `ApiDocsTest` é pulado sem ele. o ci roda os testes com o perfil.

## configuração

tudo que muda entre ambientes vem de variável de ambiente:

| variável | para que serve | padrão |
| :--- | :--- | :--- |
| `DATABASE_URL` | endereço jdbc do banco | `jdbc:postgresql://localhost:5432/doisag` |
| `DATABASE_USER` | usuário do banco | `admindoisag` |
| `DATABASE_PASSWORD` | senha do banco | **obrigatória** |
| `JWT_SECRET` | chave que assina a sessão, com pelo menos 32 caracteres | **obrigatória** |
| `SESSION_DURATION_MINUTES` | minutos que a sessão dura sem uso | `120` |
| `SESSION_MAX_HOURS` | horas que uma sessão dura no máximo desde o login, mesmo sendo renovada | `12` |
| `LOGIN_MAX_FAILURES` | senhas erradas do mesmo e-mail a partir do mesmo endereço antes do bloqueio | `5` |
| `LOGIN_MAX_FAILURES_PER_ADDRESS` | senhas erradas de um endereço, somando todos os e-mails, antes do bloqueio | `20` |
| `LOGIN_MAX_FAILURES_PER_EMAIL` | senhas erradas de um e-mail, somando todos os endereços, antes do bloqueio. teto alto, só para frear ataque distribuído | `100` |
| `LOGIN_BLOCK_MINUTES` | minutos que o bloqueio do login dura | `15` |
| `PASSWORD_RESET_MAX_REQUESTS_PER_ADDRESS` | pedidos de link de senha nova do mesmo endereço antes do bloqueio, que dura o mesmo tempo do login | `10` |
| `SESSION_SECURE_COOKIE` | cookie da sessão só trafega em https. precisa combinar com o esquema do `PUBLIC_URL`: `https` com `false` ou `http` com `true` e a api não sobe | `true` |
| `ADMIN_EMAIL` e `ADMIN_PASSWORD` | conta administrativa criada na primeira subida. a senha segue a mesma regra de senha forte das outras contas; fraca, a conta não é criada e o log diz por quê | nenhuma conta |
| `ADMIN_PASSWORD_RESET` | `true` troca a senha da conta administrativa que já existe pela do `ADMIN_PASSWORD` na subida e derruba as sessões abertas. serve para quem esqueceu a senha num servidor sem e-mail; depois de entrar, tire a variável | `false` |
| `CLINIC_NAME`, `CLINIC_CNPJ` e `CLINIC_DPO_CONTACT` | razão social da clínica, CNPJ e contato do encarregado de dados, que entram no termo de consentimento no lugar dos colchetes | **obrigatórias** fora dos perfis `dev` e `test`, que sobem com os colchetes no termo e avisam no log (revisão das regras R21) |
| `SEED_DADOS_TESTE` | cria as contas de teste | `false` |
| `JPA_SHOW_SQL` | mostra o sql no console | `false` |
| `SERVER_PORT` | porta da api | `8080` |
| `PUBLIC_URL` | endereço onde as pessoas abrem o sistema, usado nos links enviados por e-mail e como único endereço aceito nas requisições com cookie que mudam dado | **obrigatória** |
| `MAIL_HOST` | servidor smtp. sem ele o e-mail não sai e o log mostra só o destinatário e o assunto | vazio |
| `EMAIL_LOG_TEXT` | `true` mostra no log o texto inteiro do e-mail, com o link de senha nova e o de confirmação do e-mail novo. só para desenvolvimento | `false` |
| `MAIL_PORT` | porta do servidor smtp | `587` |
| `MAIL_USERNAME` e `MAIL_PASSWORD` | conta que autentica no servidor smtp | vazio |
| `MAIL_FROM` | remetente dos e-mails. com `MAIL_HOST` preenchido e os dois vazios a api não sobe | o `MAIL_USERNAME` |
| `MAIL_SMTP_AUTH` e `MAIL_SMTP_STARTTLS` | autenticação e tls do smtp. com o starttls ligado ele é obrigatório: servidor que não oferece tls não recebe a senha nem o link. um servidor local de teste costuma pedir `false` nos dois | `true` |

a api trabalha sempre no fuso `America/Sao_Paulo`, independente da máquina onde roda. o front segue o mesmo fuso: o hoje e o agora das telas são os de Brasília, mesmo com o navegador em outro fuso. sempre que o fuso do navegador não é `America/Sao_Paulo`, mesmo outro de UTC-3 como `America/Fortaleza`, aparece "(horário de Brasília)" do lado do horário da consulta nas telas de consultas e do painel do paciente e na página de avisos, que o prescritor também vê.

## sessão e perfis

| rota | o que faz |
| :--- | :--- |
| `POST /auth/login` | confere e-mail e senha, grava o cookie `session` e devolve `{id, name, email, role, termPending, termPendingByAge}`. o `email` é o da própria conta: quando a sessão vence com uma tela aberta, o frontend entra de novo por cima dela só nessa conta (#151) |
| `POST /auth/logout` | apaga o cookie e encerra as sessões abertas da pessoa em qualquer aparelho |
| `GET /auth/me` | quem está logado. `termPending` diz se o paciente precisa aceitar o termo de novo: a versão é antiga, ou o aceite é de outra faixa de idade porque a data de nascimento cruzou os 18 anos. `termPendingByAge` diz que é só pela faixa de idade, e aí a data errada ainda se corrige no `PUT /profile` |
| `POST /auth/register` | cadastro do paciente pelo link de convite, já entrando logado. `guardian` (nome, parentesco e telefone de familiar ou cuidador) é opcional, e o `socialName` (nome social) também. se a `birthDate` dá menos de 18 anos, o `guardian` é o responsável legal e o nome e o parentesco dele são obrigatórios, e o `researchTermVersion` é recusado |

- o cookie é `httpOnly` e `SameSite=Strict`: o javascript não lê o token e outro site não consegue usar a sessão
- com `SESSION_SECURE_COOKIE=true` o cookie se chama `__Host-session` e leva `Secure`: o navegador recusa um cookie `__Host-` sem `Secure`, com `Domain` ou fora de `Path=/`, então servidor configurado errado aparece na hora em vez de um login que não gruda. em `false` (só http, no próprio computador) ele se chama `session`
- além disso, requisição que muda dado (`POST`, `PUT`, `PATCH` e `DELETE`) com o cookie da sessão só passa se o cabeçalho `Origin`, ou o `Referer` quando ele não vem, for o endereço do `PUBLIC_URL`. vinda de outro endereço recebe `403`. isso cobre navegador antigo e subdomínio vizinho, que o `SameSite` não pega, e por isso o sistema precisa ser aberto pelo mesmo endereço do `PUBLIC_URL`: em desenvolvimento, `localhost` e não `127.0.0.1`
- a sessão é renovada enquanto a pessoa usa o sistema, então ninguém é derrubado no meio de um formulário, mas ela termina 12 horas depois do login
- sair da conta encerra as sessões abertas daquela pessoa em qualquer aparelho, mesmo que alguém tenha guardado o cookie
- depois de 5 senhas erradas do mesmo e-mail a partir do mesmo endereço, as tentativas desse e-mail vindas dali ficam bloqueadas por 15 minutos, mesmo com a senha certa. 20 erros de um endereço, somando e-mails diferentes, bloqueiam o endereço inteiro
- o bloqueio não fica na conta: quem erra a senha de outra pessoa não trava o login dela de outro lugar. a exceção é o ataque distribuído: 100 erros no mesmo e-mail, somando todos os endereços, bloqueiam aquele e-mail por 15 minutos em qualquer lugar. e-mail sem cadastro é bloqueado do mesmo jeito, então a resposta não revela quem tem conta, e o link de senha nova libera o e-mail na hora
- a mesma contagem vale para toda rota que confere senha: trocar a senha, trocar o e-mail e o link de senha nova gerado pelo administrador. sessão esquecida aberta não vira chute livre da senha atual
- trocar o e-mail de acesso não troca nada na hora: a api guarda o pedido, avisa o e-mail antigo e manda um link para o novo, e o e-mail só muda quando esse link é aberto. a resposta é a mesma exista ou não conta com o endereço novo (nesse caso o link só não sai), então um paciente logado não descobre quem é da clínica. 5 pedidos em 15 minutos bloqueiam o sexto
- o cadastro com e-mail ou CPF que já tem conta responde `400` com uma mensagem só, sem dizer qual dos dois, e o convite continua valendo para os dados certos. 5 tentativas no mesmo convite, ou 20 recusas do mesmo endereço, bloqueiam o cadastro por 15 minutos. a mensagem genérica sozinha não esconde tudo: uma tentativa com o CPF de alguém ainda diz se ele tem conta, e o que segura é o convite ser pessoal e a contagem
- a conta administrativa não troca de e-mail pelo perfil, porque o e-mail dela é o `ADMIN_EMAIL` do servidor: trocando por fora, a subida seguinte criaria outra conta com a senha inicial
- a senha vai de 8 a 64 caracteres e precisa caber em 72 bytes, que é o limite do bcrypt. letra com acento e emoji ocupam mais de um byte, e a senha que não cabe é recusada com mensagem no próprio campo
- a contagem fica na memória da api, que roda numa instância só, e zera quando ela reinicia. atrás do nginx o endereço de quem acessa vem do cabeçalho `X-Forwarded-For`, então um proxy a mais na frente precisa repassar esse cabeçalho, senão todo mundo aparece com o mesmo endereço
- a contagem guarda só o hash do e-mail, que tem sempre o mesmo tamanho. além disso o login aceita no máximo 255 caracteres no e-mail, o tamanho da coluna, e 255 na senha, e o pedido de link de senha nova também para nos 255 do e-mail: acima disso a resposta é `400` no campo, antes de qualquer contagem. sem isso cada login errado com um e-mail gigante ficava 15 minutos na memória e um punhado de endereços derrubava a api
- o e-mail que cria ou troca o acesso de uma conta (cadastro, troca de e-mail no perfil, criação de prescritor e correção do e-mail dele pela administração) precisa ter ponto depois do `@`: `maria@gmail` é recusado no campo, porque o link de senha nova e os lembretes nunca chegariam lá. o `@Email` sozinho aceita esse endereço. o login e as buscas pelo e-mail não conferem isso, porque só acham o que já está guardado
- o CPF do cadastro e da conta de prescritor criada pela administração é conferido pela própria api, sem biblioteca (`@ValidCpf`, com a conta em `CpfRules`): os dois dígitos verificadores pela regra do módulo 11, e a sequência de um número só repetido é recusada mesmo fechando a conta. a api recebe só os 11 números, mas a máscara inteira `000.000.000-00` também passa, como antes; qualquer outra forma é recusada no campo, e o vazio fica com o `@NotBlank`. o navegador faz a mesma conta antes de enviar, só para avisar na hora
- conta desativada perde o acesso na requisição seguinte. a sessão dela recebe o `401` com o motivo do login, *Conta desativada. Fale com a clínica*, e o cabeçalho `X-Account-Deactivated: true`, para a tela aberta dizer o motivo em vez de pedir a senha de novo (decisão de 13/11/2026). só a sessão da própria conta, dentro do prazo e emitida depois da última troca de senha e da última saída da conta (ou troca de e-mail), fica sabendo: sem sessão, com a sessão vencida, com a de antes da troca de senha ou com a que a saída da conta já tinha encerrado, a resposta é o `401` genérico de sempre, porque esse cookie pode ter ficado com outra pessoa. por isso a desativação não encerra as sessões, quem encerra é a reativação: gravando o fim das sessões na desativação, a hora da saída feita antes se perdia. o **Sair** do aviso de acesso encerrado conta como saída da conta: o `POST /auth/logout` com a sessão da conta desativada também encerra as sessões dela, então o valor desse cookie, copiado antes por alguém, passa a receber o `401` genérico
- o frontend manda em cada requisição o cabeçalho `X-Session-User` com o id da conta que a tela aberta mostra. o cookie é um só para todas as abas do navegador, e outra aba pode ter saído e entrado em outra conta, como o responsável com dois filhos (#152): quando o cabeçalho vem e não é o dono da sessão, a requisição segue sem sessão e recebe o `401` genérico, sem o motivo da conta desativada, então o que foi digitado para uma conta não grava na ficha da outra (RF30). o cabeçalho só tira a sessão, nunca cria nem amplia uma: sem cookie ele não faz ninguém entrar. o login, o cadastro e a saída da conta não mandam esse cabeçalho
- testes e ferramentas podem mandar o mesmo token no cabeçalho `Authorization: Bearer`, que não passa pela conferência de origem porque o navegador não manda esse cabeçalho sozinho

os perfis são `PATIENT`, `PRESCRIBER` e `ADMIN`. a autorização tem duas camadas:

- o `SecurityConfigurations` barra pelo perfil antes de chegar no controller: o administrador só entra em `/admin/**` e nos dados da própria conta, e as outras rotas são de paciente e prescritor
- cada rota declara no `@PreAuthorize` os perfis que podem usá-la e, quando o dado é de um paciente, confere o vínculo no `PatientAccessService`: o paciente só vê os próprios dados e o prescritor só vê os pacientes vinculados a ele

o `RouteRolesTest` passa por todas as rotas da api e falha se alguma não declarar perfil. o `PatientLinkTest` cobre as regras de vínculo, inclusive trocando o id na url.

## administração

| rota | o que faz |
| :--- | :--- |
| `GET /admin/prescribers` | lista os prescritores |
| `POST /admin/prescribers` | cria conta de prescritor, sem senha. o link de primeiro acesso só volta na resposta quando o e-mail não saiu. o conselho é guardado em maiúsculas e o número do registro sem espaço nas pontas, e a combinação dos dois que já tem conta responde `409` no campo `registryNumber` |
| `PUT /admin/prescribers/{id}` | corrige o registro profissional, a profissão e o CPF de um prescritor digitados errado. o conselho e o número passam pela mesma limpeza e unicidade do cadastro (`409` em `registryNumber` ou em `cpf`), o CPF pela mesma conferência dos dígitos, e em branco ele fica como está, porque a lista não mostra o CPF. a correção vai para a trilha como `ALTERACAO` de `CONTA_DE_PRESCRITOR` |
| `PUT /admin/prescribers/{id}/active` | ativa ou desativa a conta, sem apagar nada |
| `PUT /admin/prescribers/{id}/email` | corrige o e-mail digitado errado de um prescritor que ainda não criou a senha, com a senha do administrador. o link de primeiro acesso sai de novo para o endereço certo e o anterior deixa de valer. depois que a pessoa criou a senha, só ela troca o e-mail, no perfil |
| `POST /admin/prescribers/{id}/password-reset` | gera um link de senha nova para um prescritor. o link só volta na resposta quando o e-mail não saiu. para a conta que ainda não criou a senha, o e-mail diz que é esse link que cria a primeira senha, em vez de "a sua senha continua a mesma" |
| `POST /admin/patients/lookup` | acha a conta de um paciente pelo e-mail inteiro, que vai no corpo. devolve só `{id, name, email, active}`, e o `civilName` quando o paciente tem nome social. a busca que acha a conta vai para a trilha como `VISUALIZACAO` de `CONTA_DE_PACIENTE`, com o número do paciente e o `detail` *Busca da conta pelo e-mail*, e aparece também na trilha do prontuário dele (revisão das regras R20) |
| `GET /admin/patients/deactivated` | as contas de paciente desativadas, em ordem alfabética do nome mostrado, para dar para reativar depois. cada abertura vai para a trilha como `VISUALIZACAO` de `CONTA_DE_PACIENTE`, sem paciente, com o `detail` *Lista das contas desativadas* (revisão das regras R20) |
| `PUT /admin/patients/{id}/active` | ativa ou desativa a conta de um paciente e devolve a conta como a busca. pedir o estado que a conta já tem responde `400`, sem a conta |

o administrador não acessa nenhum dado clínico.

o administrador não escolhe nem conhece a senha de ninguém. a conta de prescritor nasce com uma senha aleatória que ninguém vê, e quem cria a senha de verdade é o próprio prescritor, pelo link de primeiro acesso: uso único, 48 horas, o mesmo mecanismo do link de senha nova. com `MAIL_HOST` o link vai só para o e-mail da pessoa; sem ele, aparece na tela para o administrador entregar. se vencer, o **Senha nova** gera outro. a criação da conta fica na trilha como `CRIACAO` de `CONTA_DE_PRESCRITOR`.

desativar uma conta, de prescritor ou de paciente, tira o acesso na requisição seguinte, e reativar encerra as sessões de antes, então a sessão antiga não volta junto com a conta (a desativação não encerra, para não apagar a hora da última saída da conta, seção sessão e perfis). as duas ações vão para a trilha (`DESATIVACAO` e `REATIVACAO`), e a de paciente aparece também na trilha do prontuário dele, para o prescritor ver. a administração não tem lista de pacientes: ela acha a conta pelo e-mail e só enxerga a lista das que desativou. por isso ativar a conta que já está ativa, ou desativar a que já está desativada, responde `400` sem nome nem e-mail: antes isso devolvia a conta sem gravar nada na trilha, e bastava passar os números da trilha um por um para saber de quem era cada um. a tela sempre manda o contrário do estado que mostra, e cada mudança de verdade continua indo para a trilha. desativar não é arquivar: arquivar é ato clínico do prescritor e não tira o acesso. a conta desativada para de receber e-mail de lembrete e escala nova do acompanhamento; os avisos dentro do sistema continuam sendo criados. nos dois casos o acompanhamento só pausa e volta de onde parou quando a conta for reativada, com o fim na mesma data: desativar o prescritor não encerra mais o acompanhamento dos pacientes dele (revisão das regras R18, 14/11/2026). desativar o prescritor também não fecha nem cancela nada dos pacientes dele: a escala esperando resposta continua pendente, a consulta marcada e o pedido esperando resposta ficam na agenda, e os prazos correm como sempre. o que para são os lembretes: enquanto a conta do prescritor estiver desativada, nenhum lembrete de formulário ou de consulta (aviso ou e-mail) sai para os pacientes dele, porque ninguém leria a resposta. reativar a conta faz os lembretes voltarem, e o que ainda couber no prazo sai na rodada seguinte do job. a escala cujo prazo venceu enquanto a conta estava desativada fecha como não respondida pelo job, como sempre. a resposta da desativação traz quantas escalas esperando resposta (`openTasks`) e quantos pedidos e consultas por vir (`futureAppointments`) ficaram com os pacientes dele, só o número, e a tela da administração mostra isso no aviso; a reativação vem sem esses dois campos. a conta de paciente desativada aparece para o prescritor dele: a lista de pacientes e o prontuário vêm com `accountActive: false`, e a tela mostra o selo "Conta desativada" na linha da lista e no cabeçalho do prontuário. nenhuma contagem muda com isso, porque só o arquivamento tira o paciente da lista.

o link de senha nova é a saída para o prescritor que esqueceu a senha antes de a clínica ter `MAIL_HOST` configurado: o administrador entrega o endereço para a pessoa pelo canal que ele confia. como a rota toma a conta de outra pessoa, ela pede a senha do próprio administrador no corpo (`adminPassword`), só funciona em conta ativa, reaproveita o link de uso único de 30 minutos e grava um evento `REDEFINICAO_DE_SENHA` na trilha de auditoria. quando o e-mail sai de verdade, o link vai só para o prescritor e a resposta vem com `resetLink` nulo, para o administrador não ficar com a conta de outra pessoa na mão. se o servidor de e-mail falhar, o link volta na resposta do mesmo jeito que sem `MAIL_HOST`, senão o prescritor ficaria trancado até alguém consertar o SMTP.

## perfil

| rota | o que faz |
| :--- | :--- |
| `GET /profile` | dados da própria conta |
| `PUT /profile` | nome, data de nascimento, telefone e endereço. o paciente também manda o `guardian` e o `socialName`: mandar sem o `guardian` apaga o que estava salvo, e o `socialName` em branco ou ausente apaga o nome social. paciente com menos de 18 anos não pode ficar sem o nome e o parentesco do responsável legal, e a `birthDate` de um menor retira o consentimento de pesquisa que estiver valendo. a `birthDate` trocada pelo paciente vai para a trilha como `ALTERACAO` de `CONTA_DE_PACIENTE`, com a data antiga e a nova no `detail`, e a que muda a faixa de idade (menor para adulto ou o contrário) avisa o prescritor, *Faixa de idade mudou* (revisão das regras R9). as outras contas ignoram o `socialName` |
| `PUT /profile/email` | pede a troca do e-mail de acesso, com a senha atual. devolve o perfil com o endereço novo em `pendingEmail`; o e-mail só muda quando o link enviado para ele é aberto (`POST /auth/email-change/confirm`) |
| `PUT /profile/email-preference` | liga ou desliga os lembretes por e-mail. só o paciente, que é o único que recebe esses e-mails; as outras contas recebem `403` |
| `PUT /profile/password` | troca a senha pedindo a atual. as outras sessões caem e este aparelho continua logado |

as rotas de perfil usam sempre a conta da sessão, então ninguém altera o perfil de outra pessoa.

o perfil, a troca de senha, a saída da conta, o aceite do termo e a ativação ou desativação pela administração mexem na mesma linha da conta, e cada um lê a conta e só grava no fim. as entidades de conta (`Users`, `Patient`, `Prescriber` e `Admin`) têm `@DynamicUpdate`, então o update grava só as colunas que aquela ação mudou e o que outra ação gravou no meio fica: o perfil salvo logo depois de uma desativação não reativa a conta, a senha nova não volta para a antiga, a desativação salva logo depois do perfil não traz de volta o nome antigo e a sessão derrubada não volta. a anotação não passa do `Users` para as subclasses, por isso cada uma repete. pelo mesmo motivo nenhum serviço salva a conta da sessão (`@AuthenticationPrincipal`), que foi lida no começo da requisição: ele recebe o id e lê a conta dentro da própria transação. o `ProfileRaceTest` e o `LogoutRaceTest` conferem essas corridas.

o nome social é opcional e só o próprio paciente informa, no cadastro ou no perfil (RN15). nome social em branco ou igual ao nome civil não é guardado. o nome do paciente nas respostas é sempre o nome mostrado: `name`, `patientName` e o `actorName` da trilha trazem o nome social quando ele existe e o civil quando não existe, e os avisos e os e-mails usam o mesmo nome. o perfil é a exceção: lá `name` é o nome civil, que é o campo editável, e o social vem em `socialName`. o nome civil só aparece junto do social onde o registro identifica a pessoa: o `GET /patients/{patientId}` e todas as rotas de paciente da administração (busca, lista das desativadas e ativar ou desativar) devolvem também o `civilName`, que só vem quando o paciente tem nome social. a lista de pacientes do prescritor não leva o `civilName`.

## recuperação de senha

| rota | o que faz |
| :--- | :--- |
| `POST /auth/password-reset/request` | manda o link de senha nova para o e-mail, se ele for de uma conta ativa. a resposta é sempre a mesma. para o prescritor que ainda não criou a senha, o e-mail diz que é esse link que cria a primeira, como no link gerado pela administração |
| `POST /auth/password-reset/confirm` | grava a senha nova. o link vale uma vez, por 30 minutos, e as sessões abertas caem |
| `POST /auth/email-change/confirm` | confirma o e-mail de acesso novo pelo link que chegou nele, sem login. o link vale uma vez, por 30 minutos; na confirmação o e-mail muda, as sessões abertas caem, o link de senha nova que tiver ido para o endereço antigo deixa de valer e o endereço antigo recebe um aviso |

cada conta recebe no máximo 3 links por hora e um link novo cancela os anteriores. o pedido também conta por endereço, exista ou não a conta: depois de 10 pedidos em 15 minutos o endereço recebe `429`. o e-mail sai depois da resposta, em segundo plano, para a espera pelo servidor de e-mail não denunciar que a conta existe. sobra uma diferença de poucos milissegundos de banco entre os dois caminhos, que o limite por endereço torna difícil de medir. o e-mail sai pelo servidor configurado em `MAIL_HOST`. sem ele, o e-mail não sai: o log mostra só o destinatário e o assunto, e o texto com o link só aparece com `EMAIL_LOG_TEXT=true`, que a api local com banco em memória já liga.

a troca do e-mail de acesso segue o mesmo desenho: o pedido guarda o endereço novo com o hash do código, um pedido novo cancela o anterior, trocar a senha (pelo perfil ou pelo link de senha nova) também cancela, e o endereço só vira o e-mail da conta quando o link é aberto e o endereço ainda está livre. sem `MAIL_HOST` o link de confirmação vai só para o log, igual ao de senha nova: a troca nunca é direta, porque é o link que prova que a pessoa recebe e-mail naquele endereço.

| rota | o que faz |
| :--- | :--- |
| `POST /invites` | o prescritor gera um link de convite de uso único, válido por 7 dias |
| `GET /invites` | os convites do prescritor que ainda podem ser usados, sem o código |

## termo de consentimento

| rota | o que faz |
| :--- | :--- |
| `GET /consent-term` | rota pública com a versão, o texto do termo que o cadastro pede e o sha-256 desse texto (`textHash`) |
| `POST /consent-term/accept` | o paciente com o termo pendente (versão antiga ou aceite de outra faixa de idade) aceita a atual (`termVersion` e `termHash` no corpo) e recebe de volta os dados da sessão. o `guardian` (nome, parentesco e telefone) é opcional e só é usado quando o paciente tem menos de 18 anos e ainda não tem responsável salvo, ou tem sem o parentesco: aí o nome e o parentesco são obrigatórios e ficam salvos no paciente antes do aceite |
| `GET /consent-term/research` | rota pública com a versão, o texto do consentimento de pesquisa, que é opcional, e o `textHash` dele |
| `POST /consent-term/research/accept` | o paciente aceita participar da pesquisa (`termVersion` e `termHash` no corpo). paciente com menos de 18 anos recebe 400 até o comitê de ética definir o assentimento do menor |
| `POST /consent-term/research/revoke` | o paciente retira o consentimento de pesquisa. a linha fica com a data da retirada |

o texto fica em `src/main/resources/consent/termo-de-consentimento.txt` e ainda é um rascunho que a clínica precisa aprovar. `[NOME DA CLÍNICA]`, `[CNPJ DA CLÍNICA]` e `[CONTATO DO ENCARREGADO DE DADOS DA CLÍNICA]` saem de `CLINIC_NAME`, `CLINIC_CNPJ` e `CLINIC_DPO_CONTACT`. fora dos perfis `dev` e `test` a api não sobe sem as três, como sem `JWT_SECRET` e `PUBLIC_URL`: no ar com os colchetes, os primeiros pacientes aceitariam um termo sem a clínica e não seriam chamados a aceitar de novo. no `dev` e no `test` ela sobe com os colchetes no texto e avisa no log. quando o texto mudar, troque também `ConsentTermService.CURRENT_VERSION`: cada aceite fica guardado com a versão e a data, e também com o sha-256 do texto mostrado, já com os dados da clínica (`consent_acceptance.term_hash`), porque trocar uma dessas variáveis muda o texto sem mudar a versão. o hash prova qual texto a pessoa aceitou sem pedir aceite novo a ninguém; o aceite de outra versão e os gravados antes de 14/11/2026 ficam sem ele (revisão das regras R21). por isso o aceite manda de volta o `textHash` que veio com o texto (`consentTermHash` e `researchTermHash` no `POST /auth/register`, `termHash` nos dois aceites): se a api reiniciou com outro dado da clínica depois que a tela abriu, o hash não bate e o aceite recebe o mesmo `400` da versão desatualizada, sem gravar nada, então o hash guardado é sempre o do texto que a pessoa leu. o aceite sem o hash também recebe esse `400`. o paciente cujo último aceite é de uma versão antiga, ou de outra faixa de idade (veja abaixo), recebe `termPending: true` no login e no `GET /auth/me`, e até aceitar a nova a api só deixa ele ler: qualquer outra requisição que grava, fora `/auth`, `/consent-term`, o `POST /invites/lookup` e, com a pendência só pela faixa de idade, o `PUT /profile` (veja abaixo), responde 403 com o cabeçalho `X-Term-Pending: true` e a mensagem "Leia e aceite o termo de consentimento para continuar", a mesma nos dois casos, e o front abre o termo por cima da tela sem perder o que já foi preenchido. conferir o convite fica de fora porque é rota pública e a tela de cadastro a chama com outra conta aberta, como o responsável que abre o link do segundo filho sem ter aceitado o termo novo na conta do primeiro.

paciente com menos de 18 anos (pela `birthDate`, no horário de Brasília, em anos completos) tem o responsável legal no aceite do termo (LGPD, art. 14, e Código Civil): com menos de 16 anos o responsável aceita em nome do paciente, e com 16 e 17 o paciente aceita junto com ele. a api guarda igual nas duas faixas, e só o texto da tela muda. cada aceite de menor guarda em `guardian_name` e `guardian_relationship` o responsável salvo no paciente naquele momento; aceite de adulto, mesmo com cuidador, fica com os dois nulos. menor sem responsável salvo, que só existe em conta de antes dessa regra, manda o `guardian` no `POST /consent-term/accept`, porque com o termo pendente pela versão o `PUT /profile` fica bloqueado; sem ele o aceite recebe 400 no campo `guardian.name`. o mesmo vale para o menor com o nome do responsável salvo e sem o parentesco, de conta criada quando o parentesco ainda era opcional: a tela traz o nome preenchido, e sem o `guardian` o aceite recebe 400 no campo `guardian.relationship`. nenhum aceite de menor é gravado sem o nome e o parentesco. menor também fica fora da exportação sem identificação, mesmo com um aceite de pesquisa antigo valendo.

o aceite que vale é o último `REGISTRATION` da versão atual, e ele precisa combinar com a idade de hoje: menor com `guardian_name` preenchido, adulto com ele nulo. a data de nascimento que cruza os 18 anos, corrigida no `PUT /profile` ou pelo aniversário, volta o `termPending` para `true`, e o `POST /consent-term/accept` grava outro aceite da mesma versão, com ou sem o responsável conforme a faixa. aceitar de novo na mesma faixa não duplica o registro. pendente só pela faixa (o texto atual já foi aceito, por outra faixa), o `PUT /profile` continua liberado e o `GET /auth/me` traz `termPendingByAge: true`: a data digitada errada se corrige sem gravar antes um aceite na faixa errada, como o de uma criança sem o responsável, e com a data certa o aceite que já existia volta a valer. pendente pela versão, o perfil continua bloqueado. a pendência que veio do aniversário de 18 anos (o aceite é de menor, pela data de hoje o paciente ainda era menor quando aceitou, e a trilha não tem troca da data de nascimento depois desse aceite) conta como a da versão: `termPendingByAge` vem `false`, a tela não oferece *Corrigir a data* e o perfil fica bloqueado até o aceite de adulto, porque a data não mudou e o responsável que ainda usa a conta não pode voltar a data para fugir desse aceite. a data trocada no `PUT /profile` depois do aceite, mesmo que pela data nova os 18 anos caiam entre o aceite e hoje, continua pendente só pela faixa (`termPendingByAge: true`), porque pode ser o ano digitado errado, como 2008 no lugar de 2018 (revisão das regras R9).

## histórico clínico

| rota | o que faz |
| :--- | :--- |
| `GET /patients/{patientId}/anamneses` | resumo das anamneses do paciente, da mais recente para a mais antiga. na mesma data vem antes a preenchida por último, então a refeita depois de anular aparece antes da anulada. para o prescritor cada ficha traz em `corrections` as versões que as correções do paciente substituíram, da mais velha para a mais nova. para o paciente a lista vem vazia |
| `GET /patients/{patientId}/appointments` | consultas do paciente. para o próprio paciente, a anulada vem sem o registro clínico (veja abaixo) |
| `GET /patients/{patientId}/prescriptions` | prescrições do paciente, com a data da consulta que gerou cada uma. para o próprio paciente, a anulada vem sem o conteúdo (veja abaixo) |

nenhuma rota lista registros do sistema inteiro: toda lista sai filtrada pelo paciente ou pelo prescritor logado.

a consulta e a prescrição anuladas podem ser de outra pessoa lançada no paciente errado, então quando quem pede é o paciente as duas listas mandam delas só a data, a marca e o motivo: `contentHidden: true`, o registro clínico (queixa, exame físico, evolução, hipótese, conduta, exames, pressão, peso, altura e a nota do pedido) e o conteúdo da receita (produto, marca, lote, espectro, composição, volume, posologia, via, plano de dose, orientações, duração e próxima consulta) nulos ou vazios. a data, a situação, quem prescreveu e a anulação (data, autor e motivo) continuam. o prescritor recebe tudo, com `contentHidden: false`, e a anamnese e as respostas de escala, que o paciente preencheu, não mudam (decisão de 14/11/2026, revisão das regras R7).

arquivar não mexe na prescrição, que continua `VIGENTE` e `current: true`. a lista de prescrições traz `followUpEndedAt`, o dia do arquivamento, só na receita vigente de paciente arquivado, e nula em todas as outras e depois de reativar. as telas e a impressão usam esse campo para dizer "Última prescrição, acompanhamento encerrado em" no lugar de "em uso", e anular essa receita avisa o paciente com "Sua última prescrição foi anulada", também sem "em uso" (decisão de 14/11/2026, revisão das regras R2).

a receita (`POST /appointments/{appointmentId}/prescriptions`) recusa o plano de dose que pula semana: os degraus vão da semana 1 em diante, um por semana, e o primeiro fora disso recebe 400 no campo `escalationSteps[i].week` ("Preencha ou tire a semana 3"). a semana 1 é a primeira semana de uso (RN02, decisão de 14/11/2026, revisão das regras R23).

corrigir e anular a anamnese travam o paciente e depois a própria anamnese, lida de novo (`RowLock`), nessa ordem, igual às escalas: a anulação gravada enquanto o paciente corrigia aparece e a correção é recusada, e a anulação que chega no meio da correção espera e mantém o que foi corrigido. a correção guarda a ficha de antes em `anamnesis_correction`, com a data da correção, quando alguma resposta ou a data de preenchimento muda: o mesmo conteúdo enviado de novo não vira versão. `GET /anamneses/{id}` e a lista do histórico devolvem essas versões em `corrections` só para o prescritor (decisão de 14/11/2026, revisão das regras R4). a anamnese nova também trava o paciente antes de tudo, porque dá baixa na tarefa da avaliação inicial: o job que fecha a tarefa vencida trava o paciente antes de ler a tarefa, então a anamnese enviada antes das 8h fecha a tarefa como respondida, e a que chega depois do job encontra a tarefa já fechada. a anamnese nova fecha a avaliação inicial pendente e marca o dia (`answeredAt`) em toda avaliação inicial que fechou como não respondida, com ou sem uma pendente, porque a anamnese não fica ligada na tarefa como a resposta de escala e a ficha é uma só: todo envio perdido pedia a mesma ficha. essas tarefas saem das escalas vencidas do painel no mesmo dia e continuam não respondidas, então o indicador conta fora do prazo. antes só a última ganhava o dia, e a avaliação inicial perdida e enviada de novo continuava nas vencidas com a ficha já no histórico. depois da trava ela lê o paciente de novo, em vez de usar o da sessão do login: o arquivamento gravado enquanto ela esperava aparece e a anamnese é recusada. a anamnese nova avisa o prescritor ("Escala respondida", como a resposta de escala), e o aviso toma a conta dele em modo compartilhado no fim, como na escala (seção banco). anular a anamnese não reabre a tarefa da avaliação inicial, que continua respondida, então não avisa o paciente. a não respondida que ganhou o dia da anamnese atrasada também fica como está, fora das vencidas.

## agenda

| rota | o que faz |
| :--- | :--- |
| `GET /availability` | horários de atendimento da semana e duração da primeira consulta e do retorno do prescritor logado |
| `PUT /availability` | troca os horários de atendimento e as durações, de 15 a 240 minutos. `appointmentDurationMinutes` é a do retorno; sem `firstAppointmentDurationMinutes`, a primeira consulta fica com a mesma duração do retorno. cada período precisa caber pelo menos a consulta mais curta das duas, senão nunca daria horário livre: o que não cabe recebe 400 no campo `periods[i].endTime` ("O período precisa ter pelo menos 60 minutos para caber uma consulta", com a duração da mais curta), também quando a duração enviada sobe acima de um período que já existia, e nada é gravado (decisão de 13/11/2026) |
| `GET /availability/days-off` | dias sem atendimento do prescritor logado, de hoje em diante, cada um com quantos pedidos (`SOLICITADA`) e consultas (`AGENDADA`) não anulados ainda estão por vir nele |
| `POST /availability/days-off` | marca um dia sem atendimento (`date`), de hoje em diante. a resposta conta os pedidos e consultas do dia que ainda estão por vir, do mesmo jeito |
| `DELETE /availability/days-off?date=` | o dia volta a ter atendimento |
| `GET /appointments?from=&to=` | agenda do prescritor logado entre as duas datas. sem as datas, vem a agenda inteira |
| `GET /appointments/requests` | pedidos esperando a resposta do prescritor logado |
| `POST /appointments` | o prescritor marca consulta, já confirmada, para um paciente dele. sem `appointmentType`, o tipo sai do histórico do paciente, e sem `durationMinutes`, vale a duração do tipo. paciente arquivado recebe 400 ("Paciente arquivado não recebe consulta nova. Reative o paciente antes de marcar", decisão de 13/11/2026) |
| `GET /appointments/{id}` | uma consulta com os campos clínicos, para o prescritor do paciente |
| `PUT /appointments/{id}` | o prescritor remarca o pedido ou a consulta, que fica confirmada no horário novo. sem `appointmentType` e sem `durationMinutes`, os dois ficam como estavam; trocar o tipo sem `durationMinutes` usa a duração do tipo novo |
| `PUT /appointments/{id}/confirm` | o prescritor confirma o pedido, se o horário dele ainda não passou |
| `PUT /appointments/{id}/decline` | o prescritor recusa o pedido. o motivo é opcional e vai no aviso para o paciente |
| `PUT /appointments/{id}/cancel` | o paciente ou o prescritor cancela o pedido ou a consulta |
| `PUT /appointments/{id}/no-show` | o prescritor marca que o paciente não compareceu, depois que o horário passou |
| `GET /appointments/free-slots?from=&to=` | horários livres na agenda do prescritor do paciente logado, em até 31 dias. só entram os 30 dias que começam hoje (de hoje até daqui a 29 dias) e os horários que começam pelo menos 24 horas depois de agora, e o resto do período volta vazio |
| `POST /appointments/requests` | o paciente pede um horário livre, com pelo menos 24 horas de antecedência, com modalidade e motivo opcional. o pedido novo substitui o que ainda esperava resposta, que é cancelado. a troca manda em `replacedRequestIds` os pedidos que a tela mostrou e o paciente confirmou trocar (vazio ou ausente quando não havia nenhum) |
| `GET /appointments/mine` | próximos pedidos e consultas do paciente logado, com a situação de cada um |

- `inicio` e `fim` são datas no formato `aaaa-mm-dd`, as duas inclusive
- cada consulta tem um tipo, `PRIMEIRA_CONSULTA` ou `RETORNO` (nulo nas marcadas antes de o tipo existir). é primeira consulta enquanto o paciente não tem nenhuma consulta `CONCLUIDA` e não anulada; falta e cancelamento não contam. a consulta registrada depois de acontecer (`POST /patients/{patientId}/appointments`) olha só as concluídas antes dela
- os horários livres do paciente têm a duração do tipo dele. começam no início de cada período e andam no passo da consulta mais curta entre primeira e retorno, sem os que começam a menos de 24 horas de agora, sem os que se sobrepõem a um pedido ou consulta e sem nenhum em dia sem atendimento. o pedido do próprio paciente que ainda espera resposta não tira horário dele, porque o pedido novo o substitui: os horários que encostam nele continuam na lista e valem para a troca, e só o mesmo horário do pedido fica de fora. para os outros pacientes o pedido continua segurando o horário
- o dia sem atendimento não cancela nada: pedido e consulta já marcados no dia continuam valendo, e o prescritor ainda marca consulta direto nele
- o pedido do paciente segura o horário até a resposta. a recusa e o cancelamento liberam o horário
- arquivar o paciente (`PUT /patients/{id}/archive`) recusa os pedidos dele que ainda esperavam resposta, como a recusa do prescritor: o horário volta para a agenda, a mudança entra na trilha e o paciente recebe o aviso "Pedido de consulta recusado", só que dizendo que o acompanhamento foi encerrado e que ele fale com a clínica, em vez de mandar escolher outro horário. a consulta já marcada não é cancelada, porque cancelar é decisão clínica do prescritor: a resposta do arquivamento traz quantas consultas marcadas por vir ficaram (`futureAppointments`), a tela avisa, e ele cancela à mão as que não forem acontecer. nenhum lembrete de consulta sai para paciente arquivado (seção avisos e lembretes). os pedidos são travados antes do paciente e lidos de novo (seção banco, ordem das travas), então o pedido confirmado ou cancelado no mesmo instante fica como foi deixado. o pedido feito no mesmo instante também não fica aberto: o pedido do paciente trava o paciente logo depois da agenda e lê o arquivamento de novo no banco, então o que chega enquanto o arquivamento grava espera e é recusado ("Seu acompanhamento está encerrado..."). o pedido gravado entre a leitura dos pedidos e a trava do paciente fica fora da lista travada, e travar ele depois do paciente quebraria a ordem: o arquivamento confere isso já com o paciente travado e é recusado ("O paciente acabou de pedir uma consulta. Tente arquivar de novo para recusar o pedido"), sem gravar nada. na segunda vez o pedido já está na lista e é recusado junto
- o prescritor também não marca consulta nova (`POST /appointments`) para o paciente arquivado, que antes recebia "Consulta marcada" por uma chamada montada à mão, já que a tela não oferece o arquivado. a consulta marcada antes do arquivamento continua sendo remarcada e cancelada. a marcação trava o paciente logo depois da agenda e lê o arquivamento de novo no banco, como o pedido do paciente, então a que chega enquanto o arquivamento grava espera e é recusada (decisão de 13/11/2026)
- o paciente pede horário só nos próximos 30 dias contando hoje, a mesma janela da tela. o pedido para depois disso recebe 400
- o pedido do paciente é para um horário com pelo menos 24 horas de antecedência, contadas de agora, as mesmas 24 horas do cancelamento (`MIN_REQUEST_HOURS`). vale para o primeiro pedido e para a troca, e o mais cedo recebe 400 ("Escolha um horário com pelo menos 24 horas de antecedência"). o prescritor marca direto sem antecedência mínima
- o paciente tem um pedido esperando resposta (`SOLICITADA`) por vez, porque cada pedido segura um horário que some da agenda dos outros pacientes. o pedido novo substitui o que esperava, numa transação só: o horário novo é conferido como antes (livre sem contar o horário do pedido que sai, nos 30 dias, prescritor ativo, paciente não arquivado) e, só se ele passar, o anterior vira `CANCELADA` como no cancelamento pelo paciente (trilha e horário liberado) e o novo é gravado. recusado o novo, por qualquer motivo, o anterior fica como estava. pedir de novo o horário do próprio pedido recebe 400 ("Este já é o horário do seu pedido"). o pedido de antes dessa regra que ainda estiver aberto, mesmo vencido, sai junto. o prescritor recebe um aviso só, o "Pedido de consulta" do novo, com "no lugar do pedido de ..., que foi cancelado". a consulta já confirmada não conta como pedido. o limite antigo de 3 pedidos em aberto saiu (decisão de 13/11/2026)
- os pedidos em aberto do paciente são travados antes da agenda, na ordem das travas (seção banco), e lidos de novo: o pedido confirmado, recusado ou cancelado no mesmo instante fica como foi deixado e não é substituído. o pedido que outra aba do mesmo paciente gravou entre a leitura e a trava da agenda fica fora da lista travada, e travar ele depois quebraria a ordem: o pedido que chega depois é recusado com 400 ("Seus pedidos de consulta mudaram enquanto você escolhia o horário...") sem gravar nada, então dois pedidos ao mesmo tempo terminam com um só esperando resposta
- a troca só cancela o que a tela mostrou ao paciente: os pedidos em `replacedRequestIds` precisam ainda estar esperando resposta, e todo pedido do paciente que espera resposta e ainda não venceu precisa estar na lista. senão (o prescritor confirmou ou recusou o pedido depois que a tela abriu, ou outra aba fez um pedido) a API recusa com a mesma mensagem e não muda nada, em vez de cancelar calada um pedido que o paciente não viu ou de dizer que trocou uma consulta já confirmada. o pedido vencido que o job ainda não recusou não aparece na tela e sai junto sem precisar estar na lista
- pedido que passou da data sem resposta é recusado pelo job diário, com aviso para o paciente, em vez de ficar aberto para sempre. até o job passar ele não pode mais ser confirmado: o prescritor recusa, e o paciente escolhe outro horário. o job trava cada pedido e lê ele de novo antes de recusar, um por transação, então o cancelamento, a recusa, a remarcação ou a anulação gravada antes de o job ler o pedido fica valendo e o pedido não é recusado por cima. a que chega depois encontra o pedido já recusado
- o pedido para amanhã que ainda espera resposta avisa o paciente no job diário, logo depois da recusa dos vencidos: *Pedido ainda sem resposta*, "Seu pedido de consulta para ... ainda não foi confirmado. Fale com a clínica.", só dentro do sistema. sai uma vez só por pedido, porque o pedido guarda em `unanswered_notice_sent_at` a hora do aviso, e o pedido continua `SOLICITADA`. como na recusa, o job trava cada pedido e lê ele de novo, um por transação, então o pedido confirmado, recusado ou cancelado antes de o job chegar nele não recebe o aviso (decisão de 14/11/2026, revisão das regras R1)
- o sistema não é canal de urgência: as telas do paciente mostram um aviso fixo junto do motivo do pedido, das observações das escalas e da anamnese (frontend). a api não muda nada nesses textos
- a agenda (`GET /appointments`) e os pedidos (`GET /appointments/requests`) trazem `patientAccountActive`, e a tela mostra o selo "Conta desativada" na consulta ou no pedido do paciente cuja conta a administração desativou, como na lista de pacientes. desativar não fecha nada: o pedido continua esperando resposta e pode ser confirmado, e a consulta marcada continua valendo, só sem lembrete por e-mail (decisão de 14/11/2026, revisão das regras R25)
- o paciente cancela o pedido a qualquer hora e a consulta marcada até 24 horas antes. depois disso, só o prescritor cancela. o aviso do prescritor diz o que foi cancelado: "Pedido de consulta cancelado pelo paciente" para o pedido que ele ainda não tinha confirmado e "Consulta cancelada pelo paciente" para a consulta marcada
- a rota do paciente não aceita campo clínico. o motivo que ele escreve fica em `patientNote`
- cada mudança gera uma notificação para a outra parte
- a agenda de um prescritor recebe uma marcação de cada vez: marcar, pedir, confirmar, remarcar e marcar dia sem atendimento travam a linha do prescritor no banco até o fim da transação. dois pedidos do mesmo horário ao mesmo tempo não viram duas consultas: o segundo espera o primeiro gravar, lê a agenda já com a consulta nova e recebe horário ocupado (RN08). o registro da consulta feita fora da agenda (`POST /patients/{patientId}/appointments`) também trava o prescritor antes de tudo, pela ordem das travas (seção banco), e por isso dois registros ao mesmo tempo passam um de cada vez e o segundo já conta o primeiro no tipo da consulta
- a conferência de horário ocupado olha também o dia anterior: a consulta da noite que passa da meia-noite ocupa o começo do dia seguinte
- confirmar, recusar, remarcar, cancelar e marcar falta travam a própria consulta e leem ela de novo antes de decidir (`RowLock`), então o que o outro lado acabou de gravar (um cancelamento no meio da confirmação) aparece em vez de ser sobrescrito. o cancelamento trava também o paciente, logo depois da consulta, porque a trilha e o aviso dele encostam no paciente e na conta (seção banco, ordem das travas). o job diário faz o mesmo ao recusar o pedido vencido e ao mandar o lembrete da consulta de amanhã: trava a consulta e lê ela de novo, em vez de gravar por cima a consulta inteira lida antes
- só consulta confirmada e que já aconteceu recebe registro clínico (`PUT /appointments/{id}/clinical-record`), prescrição (`POST /appointments/{id}/prescriptions`) e Mini-Exame. os três usam a mesma folga de 5 minutos para o relógio
- a prescrição e o Mini-Exame lançados numa consulta ainda `AGENDADA` ou `EM_ANDAMENTO` concluem ela, como o registro do atendimento: a consulta aconteceu, então a próxima do paciente sai como retorno e o gráfico marca o dia. o registro clínico fica vazio até o prescritor preencher, e a mudança entra na trilha como alteração da consulta, sem aviso para o paciente. a consulta já está travada, e a trilha dela entra depois da trava do paciente (prescrição) ou do prescritor (Mini-Exame), pela ordem das travas
- anular a prescrição ou o Mini-Exame que concluiu a consulta, com o registro clínico ainda vazio e nenhuma outra prescrição ou Mini-Exame não anulados nela, devolve a consulta para `AGENDADA`, também na trilha como alteração da consulta e sem aviso para o paciente. o registro clínico nunca é gravado vazio, então concluída sem registro só pode ter vindo deles, e a prescrição ou o Mini-Exame anulados não contam mais como sinal de que a consulta aconteceu: sem isso a consulta em que o paciente não veio seguia contando como atendimento (a próxima saía como retorno e o gráfico marcava o dia), e a falta e o cancelamento eram recusados. com o registro preenchido, ou com outra prescrição ou Mini-Exame valendo, ela continua concluída
- a correção do registro e a remarcação (`PUT /appointments/{id}`) prendem a data de uma consulta com prescrição ou Mini-Exame não anulados, porque a prescrição vigente sai da consulta mais recente e o exame fica no dia da consulta. na correção do registro (decisão de 14/11/2026, revisão das regras R26), a consulta com prescrição recebe 400 ("Esta consulta tem prescrição e a nova data a coloca antes ou depois de outra consulta com prescrição...") só quando a nova data troca de lado com outra consulta do paciente que tem prescrição não anulada, vigente ou substituída, e a com Mini-Exame recebe 400 só quando o dia muda. corrigir só a hora no mesmo dia, ou mudar o dia sem passar por outra consulta com prescrição, passa sem anular nada. para ler as outras prescrições a correção trava o paciente depois da consulta, como o lançamento da prescrição, então a receita lançada no mesmo instante em outra consulta dele aparece. a remarcação, que sempre leva a consulta para o futuro, continua sem mudar o horário com prescrição ou Mini-Exame (400), porque os dois só existem em consulta que já aconteceu. nos dois casos o prescritor anula antes, muda a data e lança de novo, e a data compara até o minuto, como a tela manda. na remarcação, o horário novo que já passou é recusado antes dessa conferência, para o prescritor não anular a prescrição por uma remarcação que não ia passar. a remarcação também trava a consulta, então a prescrição lançada no meio dela aparece na conferência
- corrigir o registro e anular a consulta travam a consulta e leem ela de novo (`RowLock`), como a prescrição e o Mini-Exame: a prescrição lançada no meio da anulação aparece na conferência, em vez de sobrar uma prescrição vigente numa consulta anulada
- a prescrição segue a RN03 na composição: o `ISOLADO` tem um canabinoide só, o `BROAD_SPECTRUM` não tem THC, o mesmo canabinoide não aparece em duas linhas (o `OUTRO` pode, porque cada linha é um canabinoide fora da lista) e a concentração em `PERCENTUAL` vai até 100. a duração do tratamento vai até 730 dias e a próxima consulta não fica antes do dia da consulta. a recusa responde `400` no campo (`components`, `components[i].cannabinoid`, `components[i].concentration`, `treatmentDurationDays` ou `nextConsultationDate`), e o formulário confere as regras da composição antes de enviar
- a prescrição nova só vira a vigente quando a consulta dela não é mais antiga que a da vigente atual. receita lançada numa consulta anterior é gravada já como `SUBSTITUIDA`, só para o histórico, e a resposta vem com `current: false`. a prescrição trava a consulta e depois o paciente, então duas receitas lançadas ao mesmo tempo em consultas diferentes do mesmo paciente não ficam as duas vigentes. anular a vigente também grava ela como `SUBSTITUIDA`, e a resposta e a lista vêm com `status: SUBSTITUIDA`, `current: false` e `annulled: true`: a troca é só para ela deixar de contar como vigente (NOOP-04), ninguém substituiu a receita e a anterior não volta a valer sozinha. quem lê a prescrição olha `annulled` antes de `status`, como a tela, que mostra *Anulada*, e o `prescriptions.csv` (seção exportação)
- a anulação da prescrição trava a consulta, o paciente e depois a própria receita, lida de novo (`RowLock`), na mesma ordem do lançamento (consulta, paciente, receitas): a segunda anulação da mesma receita espera, encontra a receita anulada e é recusada, em vez de trocar o motivo, o autor e a data da primeira. a consulta vem primeiro porque a anulação pode devolver ela para agendada, e assim o registro ou a receita gravados nela no meio tempo aparecem e ela continua concluída. a anulação do Mini-Exame também trava a consulta dele antes do paciente
- a prescrição que passa a valer avisa o paciente ("Prescrição nova", com o link de Minhas prescrições), uma vez só, mesmo quando substitui outra; a que entra só no histórico não avisa. anular a prescrição em uso também avisa ("Prescrição anulada", pedindo para falar com a clínica antes de mudar a dose), e anular uma já substituída não, porque não muda o que o paciente toma. os dois avisos ficam só no sistema e entram depois da trilha, como nas consultas
- a falta só vale para consulta que estava `AGENDADA` e cujo horário já terminou. ela libera o horário e avisa o paciente. registrar o atendimento depois desfaz a falta e conclui a consulta, para o erro de clique não trancar o prontuário, e avisa o paciente ("Falta desfeita", com a data da falta), porque o aviso de falta pedia para ele remarcar. a correção seguinte do registro não avisa de novo. o aviso entra depois da trilha, como na falta. a agenda e o histórico do prescritor mostram "Desfazer falta e registrar atendimento" na falta, e a prescrição e o Mini-Exame só voltam depois do registro
- a falta e o cancelamento de uma consulta com prescrição ou Mini-Exame não anulados recebem 400, como a anulação e a mudança de data: eles mostram que a consulta aconteceu, e o paciente recebia o aviso de falta com a receita daquela consulta em uso. hoje os dois já concluem a consulta, então a regra pega a consulta antiga que ficou agendada com eles. no cancelamento do paciente a regra das 24 horas vem antes, e ele nunca vê essa mensagem

## escalas

as respostas de todas as escalas caem numa tabela só. o formulário de cada uma — itens, âncoras, faixas e direção — fica descrito no código, em `scale/ScaleCatalog`, e o cálculo de cada instrumento em `scale/ScaleScorer`.

| rota | o que faz |
| :--- | :--- |
| `GET /scales/definitions/{slug}` | o formulário de uma escala. o do MEEM só sai para o prescritor, e o paciente recebe 403 |
| `GET /scales/assignable` | as escalas que o prescritor pode enviar ao paciente |
| `POST /scales/{slug}/responses` | o paciente responde. no diário, responder de novo o mesmo dia corrige aquele dia |
| `GET /scales/{slug}/responses` | as respostas do paciente logado naquela escala, que a grade da semana usa. com o slug do MEEM a resposta é 403 |
| `GET /scales/responses/{id}` | uma resposta com o escore, a faixa e o valor de cada item. o MEEM só abre para o prescritor do paciente: o paciente recebe o mesmo 403 de uma resposta que não é dele. para o prescritor, `corrections` traz as versões que as correções do paciente substituíram, com a data, as respostas e o resultado de cada uma. para o paciente vem vazia |
| `PUT /scales/responses/{id}` | o paciente corrige a própria resposta enquanto o prescritor não analisou, inclusive as datas do período. o MEEM não se corrige: o prescritor anula e aplica de novo, e o paciente recebe 403, como na leitura |
| `PUT /scales/responses/{id}/review` | o prescritor marca que já conferiu, e o paciente para de editar |
| `PUT /scales/responses/{id}/annul` | anula a resposta com motivo |
| `POST /scales/mental-state-exam/appointments/{appointmentId}` | o prescritor aplica o MEEM dentro da consulta, depois que ela aconteceu. o exame só é gravado com as 11 seções e a escolaridade. os cortes são de adultos: o exame de quem tinha menos de 18 anos no dia da consulta fica com o escore e com `scoreBand` "Instrumento não validado para a idade" no lugar da faixa, e o ponto dele na evolução vem sem `cutoff` (decisão de 14/11/2026, revisão das regras R14) |
| `POST /patients/{patientId}/scales` | envia uma escala avulsa ao paciente. a escala que o paciente já respondeu hoje é recusada: a pontual com a avaliação de hoje, a de período com a semana que termina hoje e a avaliação inicial com a anamnese enviada hoje |
| `GET /patients/{patientId}/scales` | as tarefas de escala do paciente |
| `GET /patients/{patientId}/scales/overview` | o que espera resposta e o que já foi respondido. cada pendente traz `answerPath`, o link do botão de responder: o `path` da escala e, na tarefa reaberta pela anulação, com a data anulada (`?data=`) quando hoje é de outra pendente da mesma escala ou fica fora dela (a semana do diário reaberta, seção escalas). para o paciente, sem o MEEM. para o prescritor, a resposta corrigida traz `correctedAt` (a última correção) e `previousResult` (o resultado de antes dela) |
| `GET /patients/{patientId}/scales/responses` | as escalas respondidas, para o histórico. para o paciente, sem o MEEM. para o prescritor, com `correctedAt` e `previousResult` como no overview |

- cada tarefa vale por um período. o job diário fecha a que passou do prazo: com ao menos uma resposta ela conta como respondida, e sem nenhuma fica como não respondida, que no gráfico é lacuna e nunca zero (RN10). ele fecha uma tarefa por transação, travando o paciente e lendo a tarefa de novo antes de contar as respostas. a resposta ou a anamnese gravada antes de o job ler a tarefa conta, mesmo chegando no mesmo instante, e a que fica esperando o job encontra a tarefa já fechada. nos dois casos o job nunca grava não respondida por cima de uma resposta já gravada, e a tarefa que o arquivamento fechou antes dele fica como o arquivamento deixou
- a ficha de acompanhamento e o diário do sono são um registro por dia, apresentados como a grade da semana do papel. na tarefa aberta a grade cobre o período inteiro até hoje, e o paciente pode preencher de uma vez os dias que esqueceu. o dia do diário entra na tarefa pendente que cobre a data dele, e não pela do envio, então dia de outro período não conta na tarefa aberta nem cala o lembrete dela. o dia preenchido antes de existir a tarefa que cobre ele (entre a meia-noite e o job das 8h) entra nela quando ela é criada. sem pendente que cubra o dia, o dia da tarefa que fechou ontem (ou hoje) fica com ela, sem mudar a situação: a semana continua na grade do paciente até o fim do dia seguinte ao prazo, e o dia preenchido ali conta nos dias preenchidos e como atraso no indicador. a resposta guarda essa marca (`filled_late`), e o dia atrasado não segura a semana como respondida: anular o único dia no prazo reabre a semana mesmo com ele, com o aviso de responder de novo, e o job das 8h que fecha a semana reaberta só conta os dias no prazo. a semana que fechou sem nenhum dia sai das escalas vencidas do painel, como a resposta atrasada das outras escalas. o dia de uma semana que fechou antes de ontem continua solto (decisão de 14/11/2026, revisão das regras R6)
- a correção de uma escala de período ou pontual vai pelo `PUT` com as datas junto: mudar a data move a mesma resposta, em vez de criar outra no dia novo como o envio faria. o dia de início identifica a resposta, então mover para cima de outra é recusado. data que não vem fica como está, e o fim que não vem junto de um início novo segue a regra do envio. no diário a data é o dia da grade e não muda na correção
- toda correção guarda a versão anterior em `scale_response_correction` (período, respostas, escore e faixa, com a data da correção), também a do dia do diário respondido de novo pelo `POST`. o mesmo conteúdo enviado de novo não vira versão. só o prescritor recebe essas versões, e a administração não tem rota para elas. o insert da versão aponta para a resposta, que já está travada (ou o paciente, no envio do mesmo dia), então segue a ordem das travas (decisão de 14/11/2026, revisão das regras R4)
- corrigir, analisar e anular travam o paciente e depois a própria resposta, lida de novo (`RowLock`), nessa ordem: a análise gravada enquanto a paciente corrigia aparece e a correção é recusada, em vez de apagar a análise. a anulação do MEEM trava antes a consulta dele, pela ordem das travas, porque pode devolver a consulta para agendada (seção agenda)
- o paciente responde uma escala de cada vez: a resposta trava a linha do paciente até o fim da transação, então dois envios do mesmo dia ao mesmo tempo (duplo toque, retry da rede) não viram duas linhas do mesmo dia. o segundo espera e corrige o dia. pelo mesmo motivo a consulta fica travada enquanto o MEEM ou uma receita é lançada nela, e a receita trava também o paciente, e o prescritor fica travado enquanto envia uma escala avulsa ou cria um acompanhamento, e enquanto o job manda a rodada de um acompanhamento dele. o MEEM trava também o prescritor, depois da consulta e antes de gravar, pela ordem das travas (seção banco)
- item em branco não é gravado, e escala validada sem todos os itens não tem escore. essa resposta pela metade é guardada com o resultado "Incompleta: sem escore", mas não vale pela tarefa: ela continua pendente, o lembrete continua cobrando e no prazo vira não respondida. completar depois, pela correção, fecha a tarefa e avisa o prescritor. o contrário também vale: a correção que deixa pela metade uma escala que estava completa tira a resposta da tarefa, que volta a pendente
- a resposta que só tem item em branco é recusada ("Responda ao menos um item da escala"), senão virava dia preenchido ou tarefa respondida sem nada
- cada valor é conferido como chegou, e nunca vira outro: número quebrado (2.9), número que passa do `int` e horário que não vem como texto são recusados com "Resposta fora da escala do item". número inteiro escrito com ponto (2.0) vale
- no diário do sono, mais tempo acordado do que tempo na cama é recusado, em vez de gravar tempo de sono negativo. dormir e levantar no mesmo horário também é recusado, com 400 e o erro no campo `horarioLevantar` ("O horário em que se levantou é igual ao de dormir. Confira os dois horários"), em vez de gravar 24 horas na cama. passar da meia-noite continua valendo, só a diferença zero é recusada (decisão de 13/11/2026)
- tempo na cama acima de 16 horas, no diário do sono e no pittsburgh, é recusado com 400 e o erro no campo do horário de levantar (`horarioLevantar` ou `horaLevantar`). no pittsburgh o mesmo horário para deitar e levantar também, e horas de sono maiores que o tempo na cama são recusadas no campo `horasDeSono`, como o diário já faz com o tempo acordado. os minutos vão até 1440 e as contagens (gotas, despertares, doses, xícaras, cigarros) até 200: acima disso a resposta é `400` com o erro no campo do item. o cálculo do pittsburgh não muda (decisão de 14/11/2026, revisão das regras R13)
- o período respondido é sempre passado: início e fim depois de hoje são recusados, e o fim que não vem, numa semana que começou há menos de 7 dias, fica em hoje
- a resposta que não é do diário entra na tarefa pendente que cobre o dia de que ela fala (a data da avaliação, ou o fim da semana respondida, que na tela é hoje). sem nenhuma, entra na pendente mais nova que já começou: a reaberta pela anulação ou a que venceu e o job das 8h ainda não fechou. assim a tarefa reaberta depois do prazo fecha com a resposta nova, em vez de virar não respondida
- sem pendente nenhuma, a resposta que chega depois de o job fechar a tarefa como não respondida (escala avulsa, última rodada do acompanhamento) fica ligada a ela, quando ela é a última tarefa daquela escala, e a tarefa continua não respondida: ela sai das escalas vencidas do painel no mesmo dia e o indicador continua contando fora do prazo. antes a resposta ficava solta e a escala ficava nas vencidas até cinco mais novas empurrarem. anular essa resposta, ou a correção que deixa ela pela metade, não reabre a tarefa, que só volta para as vencidas. a tarefa mais velha que uma já respondida não recebe resposta nova, e o diário fica fora dessa regra e tem a sua: o dia atrasado só fica com a semana que fechou ontem, marcado como atraso, e tira das vencidas a semana que fechou sem nenhum dia, que continua fora do prazo (decisão de 14/11/2026, revisão das regras R6)
- as respostas listadas (a central de escalas, o histórico, a grade da escala e a exportação) vêm da data mais recente para a mais antiga e, na mesma data, da gravada por último: anular e responder de novo no mesmo dia deixa a válida antes da anulada
- anular a resposta, de escala ou do MEEM, vai para a trilha como anulação (`ANULACAO`), como na consulta
- a anulação que devolve a tarefa para pendente avisa o paciente no sistema ("Escala para responder de novo", com o motivo e o link da tela da escala já na data anulada, `?data=`). a anulação costuma vir depois do prazo, e o job das 8h do dia seguinte fechava a tarefa como não respondida antes de o lembrete sair, então o prazo que acaba antes de depois de amanhã passa para depois de amanhã, e o aviso diz até quando. o início fica, e a resposta nova da data anulada continua caindo nela. no acompanhamento de 90 dias a rodada seguinte da mesma escala costuma estar pendente na hora da anulação e cobrir hoje: a tela sugeria hoje, e a resposta de hoje fechava a rodada nova enquanto a reaberta seguia pendente, levava lembrete de uma escala já respondida e virava não respondida. por isso o link abre a tela na data anulada (na escala de período, com o fim da resposta anulada). o cartão da central e do painel (`answerPath`) e o lembrete do prazo dessa tarefa também abrem nela, e quando outra pendente da mesma escala cobre hoje o aviso diz com qual data, ou período, responder. se a rodada seguinte do acompanhamento chega com ela ainda aberta, ela vira essa rodada, como qualquer pendente que cobre o dia da rodada. no diário o período é a semana da grade e não muda, senão os dias da semana seguinte cairiam nas duas tarefas: a semana reaberta aceita os dias dela até o job das 8h do dia seguinte, que fecha ela, sem lembrete, também quando a anulação chega antes do job do próprio dia (de madrugada, ou com o job atrasado na subida da api): o job não fecha a semana do diário que ficou sem nenhum dia no prazo por uma anulação do mesmo dia, só o do dia seguinte. a semana que ainda tem dia no prazo não foi reaberta e fecha nesse job, como sempre. o aviso diz qual dia preencher de novo e que é até amanhã de manhã, com o link abrindo a grade dessa semana nesse dia. a anulação de um dia de uma tarefa que continua aberta não gera aviso, e a da avaliação inicial não reabre a tarefa (seção histórico clínico)
- a resposta avisa o prescritor quando a escala fica completa. nas escalas de preenchimento diário o aviso é um só, quando o período fecha, dizendo quantos dias foram preenchidos. a avaliação inicial avisa do mesmo jeito quando o paciente manda a ficha, com ou sem tarefa, e a correção não avisa de novo
- o acompanhamento de 90 dias vai do primeiro ao nonagésimo dia, e o que começa hoje manda a primeira rodada na hora, sem esperar o job de amanhã. começo no passado ou no futuro fica com o job. o que terminaria antes de hoje é recusado na data de início ("O acompanhamento terminaria antes de hoje. Confira a data de início"), senão nascia vencido, sem rodada nenhuma, e segurava o acompanhamento certo até o job encerrar ele. o que já passou do fim e o job das 8h ainda não encerrou (antes das 8h, ou com a api fora do ar) não trava a renovação: o cadastro do novo encerra ele como o job faz, com a trilha, e a tela já mostra ele como encerrado. a mesma escala entra uma vez só no acompanhamento: repetida, as duas rodadas pegavam a mesma tarefa e cada uma reescrevia o prazo dela
- o fim do acompanhamento não pega o prescritor de surpresa (revisão das regras R5, 14/11/2026): o job das 8h manda a ele um aviso no sistema 7 dias antes do fim ("Acompanhamento perto do fim") e outro no dia do fim ("Acompanhamento termina hoje"), com o link da tela do acompanhamento do paciente. cada um sai uma vez só, porque o acompanhamento guarda quando o aviso saiu (`ending_soon_notice_at` e `last_day_notice_at`). o de 7 dias só sai para o acompanhamento que começou antes da última semana, e com a api fora do ar no dia do fim o aviso sai no dia em que o job encerra, como "Acompanhamento encerrado". o aviso fica só dentro do sistema e é criado mesmo com a conta do prescritor desativada, como os outros avisos. nos últimos 7 dias o cadastro também aceita a renovação: ele encerra o atual, com a trilha, e o novo começa no máximo hoje ("Para renovar antes do fim, comece o acompanhamento novo hoje"), senão ficariam dias sem escala. a escala que fica com a mesma frequência herda o `last_round_end` do atual e segue a rodada de agora, sem ser enviada de novo nem ganhar prazo novo; a que mudou de frequência começa o próprio ciclo, como na troca. antes dos últimos 7 dias continua valendo um acompanhamento por vez ("Este paciente já tem um acompanhamento em andamento"). `GET /patients/{patientId}/treatment-protocol/last`, só do prescritor, devolve o último acompanhamento do paciente, em andamento ou encerrado, para a tela preencher a renovação, e conta como abrir o prontuário
- a tarefa do diário diz que é diária (`daily`), e só ela mostra a barra de dias preenchidos na tela
- a tarefa guarda se veio do acompanhamento automático. a escala enviada à mão não adianta a próxima rodada, mas a mesma escala nunca fica pendente duas vezes. se a rodada chega enquanto uma enviada à mão ainda está aberta, ou no mesmo dia em que ela foi respondida, ela vira a rodada e ganha o prazo da periodicidade, com lembrete de novo para o prazo novo. a resposta do dia é uma só, então uma rodada nova no dia da resposta só seria corrigida por cima dela e ficaria pendente
- cada escala do acompanhamento guarda o fim do prazo da última rodada que ele mandou (`protocol_item.last_round_end`), e a próxima sai depois desse dia. o acompanhamento que substitui outro começa o próprio ciclo com a periodicidade nova, em vez de esperar a rodada do anterior vencer: a escala que ainda espera resposta da rodada anterior vale pela primeira rodada, e a respondida no dia também. essa tarefa fica com o prazo da rodada nova, para mais ou para menos, e volta a poder receber o lembrete: o fim da tarefa que o paciente tem é sempre o `last_round_end` do item, senão o diário trocado no meio da semana, ou a Hamilton semanal trocada por mensal, acabava no prazo antigo e os dias até a rodada seguinte ficavam sem tarefa
- a escala que fica de fora do acompanhamento novo para de ser cobrada na hora da troca: a rodada pendente dela fecha no dia, pela mesma regra do arquivamento (com resposta, respondida; sem resposta, não respondida, com o prazo encurtado para hoje), então ela sai de esperando resposta, não recebe lembrete e o job não manda ela de novo. a que fecha sem resposta ganha o dia marcado (`answered_at`), como a avaliação inicial perdida que recebe a ficha atrasada: assim ela não vira escala vencida no painel e o indicador deixa ela de fora, nem a favor nem contra a meta, porque quem tirou a escala foi o prescritor e não foi atraso do paciente. a rodada que já tinha vencido antes da troca, com o job das 8h ainda sem rodar, foi atraso de verdade: ela fecha como no job, sem o dia marcado, e continua nas vencidas e no indicador. anular depois a resposta de uma escala que saiu do acompanhamento que vale agora não reabre a tarefa nem manda o aviso de responder de novo: ela fecha como na troca, sem resposta e com o dia marcado. o mesmo vale para a tarefa que o arquivamento encerrou, do acompanhamento ou enviada à mão antes dele, inclusive a semana do diário que ele fechou respondida: anular depois a resposta dela não volta a cobrar o arquivado, nem com lembrete, e ela fica fora dos indicadores. na troca do acompanhamento a escala enviada à mão não é do acompanhamento e fica como está, e a enviada à mão depois do arquivamento segue a regra de sempre
- a escala avulsa que o paciente já respondeu hoje não é enviada de novo no mesmo dia: o envio é recusado com "Esta escala já foi respondida hoje. Veja a resposta no histórico do paciente", e a tela de envio mostra o motivo na própria escala. na pontual conta a avaliação com a data de hoje, e na de período (`REGISTRO_DOR`, `REGISTRO_TEA`) a semana que termina hoje, porque a tela e o servidor mandam o início seis dias antes. a resposta do dia é uma só, então a tarefa nova ficaria pendente e responder de novo só corrigiria a primeira. na avaliação inicial conta a anamnese não anulada enviada hoje, seja qual for a data de preenchimento, senão a tarefa nova pedia uma segunda ficha: a ficha nova sempre vira outra anamnese, e a data de preenchimento é o paciente que escolhe. a resposta anulada, a de outra data (a semana que terminou ontem, na de período) e o dia do diário não seguram o envio
- limite conhecido: o paciente que responde antes do job das 8h a rodada que venceu ontem (às 7h, por exemplo) fecha essa rodada, e a rodada nova que o job manda às 8h só fecha com a resposta de outro dia, porque responder de novo com a data de hoje corrige a das 7h. a rodada nova vale pelo prazo da periodicidade, então o paciente responde a partir do dia seguinte
- paciente arquivado não recebe a avaliação inicial, porque não consegue mandar a ficha: o envio é recusado até ele ser reativado. as outras escalas enviadas à mão continuam chegando
- o escore de escala validada sai do algoritmo oficial do instrumento e vem sempre com a faixa (RN13 e RN14)
- o MEEM é de heteroaplicação: só o prescritor aplica, dentro de consulta confirmada, e ele nunca vira tarefa do paciente (RN09)
- o paciente não vê o MEEM, nem chamando a API direto, e o resultado é conversado na consulta (decisão de 13/11/2026, §8.3 dos requisitos). a regra fica em `ScaleType.isHiddenFrom`: as listas do paciente (central de escalas, histórico, `scales.csv` e o catálogo do progresso) vêm sem o exame, e o que ele pede direto (a resposta pelo número, a lista e o formulário com o slug `mini-exame`, a série e o `progress.csv` do `ESCORE_MEEM`) recebe 403 com *Acesso negado*, o mesmo de um dado que não é dele. a resposta pelo número passa pelo `scaleAccess`, então ele não descobre nem que o exame existe. o prescritor do paciente continua vendo tudo, como antes. as marcas de consulta e os comentários do progresso não falam do exame: a marca traz só a data, a modalidade, a situação, o diagnóstico e se saiu receita, e o MEEM não tem item de texto livre
- o MEEM é a exceção à regra do item em branco: como não tem correção, exame com seção ou escolaridade em branco é recusado com a lista do que falta, em vez de ser gravado sem escore ou sem faixa (RN14)

## exportação

| rota | o que faz |
| :--- | :--- |
| `GET /patients/{patientId}/export/appointments.csv` | as consultas do paciente que entram no histórico, com a conduta de cada atendimento |
| `GET /patients/{patientId}/export/prescriptions.csv` | as prescrições, com prescritor, composição, posologia, plano de dose, instruções, precauções, efeitos esperados e vigência |
| `GET /patients/{patientId}/export/scales.csv` | as escalas respondidas, uma linha por item, com o escore e a faixa |
| `GET /patients/{patientId}/export/anamneses.csv` | a anamnese, uma linha por pergunta respondida |
| `GET /patients/{patientId}/export/progress.csv?attribute=&period=` | a série de um atributo no período, com a faixa ao lado do escore |

- todas aceitam `deidentified=true`, que é a exportação sem identificação, para pesquisa: sai sem nome, CPF, e-mail, telefone e endereço, e o paciente e o prescritor aparecem só por um número. só o prescritor pode pedir esse modo, e só de paciente que aceitou a versão atual do consentimento de pesquisa e não retirou (RF37). texto livre, como queixa e observação, sai como foi escrito. não é anônimo: o número é o id do banco e a clínica sabe de quem é, então pela LGPD o arquivo continua sendo dado pessoal de saúde (art. 12). o parâmetro antigo `anonymous` responde 400, para uma aba desatualizada não baixar o arquivo com nome
- no arquivo com identificação, o paciente com nome social sai como `Nome social (nome civil: Nome civil)` na coluna `Paciente`. o arquivo sem identificação não leva nenhum dos dois
- o arquivo vai como anexo, separado por ponto e vírgula e com marca de UTF-8, que é como a planilha abre com acento certo
- o `appointments.csv` segue a mesma regra do histórico e da impressão: entra a consulta que já passou e foi atendida, estava marcada ou virou falta; pedido sem resposta, recusado, cancelada e consulta futura ficam de fora, para o arquivo não misturar pedido com atendimento feito. a anulada entra marcada, como no histórico (07/11/2026, #147)
- no `prescriptions.csv` a composição sai como a tela mostra, `CBD 10% + THC 0,3% + CBG 25 mg/mL`: vírgula decimal, sem os zeros que o banco guarda (`10.000` seria lido como dez mil) e a unidade escrita, não o nome do enum
- as colunas de código também saem com o texto da tela: `Modalidade` (*Presencial*, *Remota*) e `Situação` (*Agendada*, *Em andamento*, *Concluída*, *Falta*) no `appointments.csv`, `Situação` (*Vigente*, *Substituída*, *Anulada*) e `Espectro` (*Isolado*, *Broad spectrum*, *Full spectrum*) no `prescriptions.csv` e `Atributo` no `progress.csv`, com o nome do seletor do gráfico, como *Dor* ou *Escore total*. o nome do enum vai na coluna ao lado (`Código da modalidade`, `Código da situação`, `Código do espectro` e `Código do atributo`), que é o que não muda para quem filtra na planilha (revisão das regras R16). a receita anulada tem o código `ANULADA`, e não o `SUBSTITUIDA` gravado. a receita anulada sai como *Anulada*, mesmo a vigente, que a anulação passa para `SUBSTITUIDA` só para ela deixar de contar como vigente: ninguém substituiu a receita, e quem lê só a situação concluiria que veio uma nova. na consulta anulada a `Situação` continua a de antes, como *Concluída*, porque anular não troca a situação da consulta: a anulação fica nas colunas `Anulada` e `Motivo da anulação`, enquanto a tela mostra o selo *Anulada* (13/11/2026)
- o `Peso` do `appointments.csv` sai com vírgula decimal e sem zero à toa, como a tela mostra (`72,5` e `80`): com ponto, a planilha em português lê `72.5` como texto e não soma nem tira média. o `Valor` do `progress.csv` é sempre um número inteiro e sai como está
- no `scales.csv` a `Resposta` sai com o texto da tela (minutos como `7h30`, *Sim* e *Não*, o rótulo da opção) e o `Código` ao lado com o valor guardado. as horas, que aceitam meia hora (*Horas de sono por noite* no PSQI e *Tempo fora de casa* no diário), saem com vírgula decimal e sem zero à toa nas duas colunas, `6,5` e `7`, e não `6.5` e `7.0`, que a planilha em português lê como texto ou data (revisão das regras R16)
- o `Peso (kg)` e a `Altura (cm)` do `anamneses.csv` seguem a mesma regra desde 13/11/2026: a ficha guarda a resposta como texto, do jeito que o campo numérico do navegador manda (`68.5`), e a resposta que é só um número com ponto sai com vírgula (`68,5`), por `BrazilianFormat.decimalAnswer`. a resposta escrita de outro jeito sai como está. o banco e a api continuam com o ponto, que é o que o campo numérico da correção da ficha lê
- o `prescriptions.csv` leva a receita inteira (RF05): `Prescritor` traz o nome de quem prescreveu (no modo sem identificação só o número dele), `Plano de dose` traz os degraus numa célula só, como `Semana 1: 2 gotas à noite · começar devagar; Semana 2: 4 gotas à noite`, e `Instruções de uso`, `Precauções e contraindicações` e `Efeitos esperados` saem como foram escritos. texto que começa como fórmula ganha o apóstrofo, como nas outras colunas (07/11/2026, #146)
- os quatro arquivos do histórico têm `Anulada` e `Motivo da anulação`. no `scales.csv` e no `anamneses.csv`, que têm uma linha por item, o motivo se repete em cada linha do registro anulado
- no `appointments.csv` e no `prescriptions.csv` que o paciente baixa, a consulta e a prescrição anuladas saem só com o paciente, a data (e a hora, na consulta), `Anulada` e `Motivo da anulação`, com as outras colunas em branco, pela mesma regra do histórico. o arquivo do prescritor continua inteiro (decisão de 14/11/2026, revisão das regras R7)
- no `progress.csv` a coluna `Faixa` traz a faixa gravada do escore (HAM-A, PSQI, MEEM e intensidade da dor), igual à do `scales.csv`, e fica em branco nos itens da ficha, que não têm faixa publicada (RN13 e RN14)
- cada linha do `progress.csv` traz também o que a tela mostra embaixo do nome do atributo: `Significado do mínimo` e `Significado do máximo` (`0 = muito ansioso`, `10 = tranquilo`; no escore, a primeira e a última faixa do instrumento) e `Maior é melhor` (`sim` ou `não`), que saem do mesmo catálogo do `GET /progress/attributes`. contagem e minutos não têm âncora no papel e ficam em branco nas três, em vez de um lado melhor inventado (RF27, revisão das regras R16)
- o paciente exporta os próprios dados e o prescritor os dos pacientes vinculados, pela mesma regra de vínculo das outras rotas (RF30)
- o arquivo que o paciente baixa sai sem o MEEM: o `scales.csv` dele não tem as linhas do exame e o `progress.csv` do `ESCORE_MEEM` responde 403. o direito de acesso ao prontuário inteiro (LGPD, art. 18) é atendido pela clínica: a pedido do paciente, o prescritor exporta ou imprime o prontuário completo, com o MEEM (decisão de 13/11/2026)
- cada arquivo baixado entra na trilha como `EXPORTACAO` de `PRONTUARIO`, uma linha por arquivo, sem a janela de 30 minutos da abertura de tela, com o tipo do arquivo e a marca da pesquisa no `detail` (`Consultas (appointments.csv), com identificação` ou `..., sem identificação, para pesquisa`). vale para o prescritor e para o paciente que baixa os próprios dados. o arquivo recusado (sem consentimento de pesquisa, o MEEM pedido pelo paciente) não grava nada, porque a recusa vem antes da linha da trilha. o `progress.csv` lê a série sem gravar a abertura do prontuário, então o arquivo é só exportação (revisão das regras R19)
- não há geração de PDF no servidor: o front tem uma página de impressão que o navegador salva em PDF. a impressão traz a seção *Prescrição em uso* com a prescrição vigente, independentemente do período escolhido, porque a receita em uso é estado e não histórico: a vigente emitida antes do período continua valendo e sumia da impressão de 90 dias (07/11/2026, #171). pelo mesmo motivo ela traz a seção *Anamnese mais recente*, com a última ficha não anulada da lista `GET /patients/{patientId}/anamneses`, também fora do período e com a data de preenchimento à vista (revisão das regras R10)

## avisos e lembretes

| rota | o que faz |
| :--- | :--- |
| `GET /notifications?page=` | os avisos da conta logada, 20 por página, com o número de não lidos |
| `POST /notifications/{id}/read` | marca um aviso como lido |
| `POST /notifications/read-all` | marca todos como lidos |
| `DELETE /notifications/{id}` | apaga um aviso da própria conta |

o aviso é sempre da conta logada: o aviso de outra pessoa responde `404`, como se não existisse, para ninguém descobrir quais ids existem.

os lembretes automáticos saem no job diário, junto com o acompanhamento de 90 dias:

- **consulta:** quem tem consulta marcada para o dia seguinte recebe o lembrete de manhã. o job de amanhã já olha o dia seguinte, então a consulta marcada, confirmada ou remarcada para amanhã recebe o lembrete na hora, com o horário novo, pelo mesmo caminho do job; antes ela ficava sem lembrete, ou só com o e-mail do horário antigo. o lembrete na hora não olha o ciclo do dia (`daily_cycle`): ele dependia de o ciclo de hoje estar concluído, e num dia em que qualquer etapa falhou a consulta ficava sem ele. sai uma vez só porque `reminder_sent_at` fica gravado na mesma transação, e o job trava a consulta e lê ela de novo antes de mandar, então pula a que já tem. a edição que mantém o horário (só modalidade, duração ou tipo) não limpa `reminder_sent_at` e não repete o lembrete. a consulta guarda em `emailed_date_time` o horário que o último e-mail dela disse ao paciente: o lembrete grava esse horário quando o e-mail sai de verdade (conta ativa e avisos por e-mail ligados). com ele preenchido, o cancelamento pelo prescritor manda também o e-mail "Sua consulta no 2AG foi cancelada", e a remarcação para outro dia, quando o horário novo não recebe lembrete na hora, manda "Sua consulta no 2AG foi remarcada", com o horário que o e-mail tinha dito e o novo, e passa a guardar o novo, então cancelar ou remarcar de novo depois também vai por e-mail. o conteúdo é o do lembrete (data, hora, nome do prescritor e o link) e o envio segue a mesma regra de conta ativa e preferência de e-mail. a remarcação que ganha o lembrete novo na hora não manda outro e-mail, a troca só da hora no mesmo dia que o e-mail disse (inclusive no próprio dia da consulta) fica só com o aviso no sistema, a consulta que nenhum e-mail citou (sem lembrete, ou com o lembrete só no sistema) continua só com o aviso no sistema e o cancelamento feito pelo próprio paciente também (decisão de 14/11/2026, revisão das regras R11)
- **formulário:** a escala que vence em até dois dias e ainda não teve resposta nenhuma gera um lembrete. a que já passou do prazo, como a semana do diário reaberta que espera o job de amanhã, não recebe. o aviso da tarefa reaberta pela anulação, quando hoje é de outra pendente da mesma escala ou fica fora dela, leva à tela da escala já na data dela, como o cartão da central. nos outros casos, e no e-mail, o link é a central. o aviso dentro do sistema diz qual escala é; o e-mail diz só que há um formulário esperando até tal dia, porque o nome da escala é dado clínico
- **dias em branco do diário:** na ficha diária e no diário do sono, que um dia preenchido calava, ontem e anteontem em branco geram o aviso "Dias em branco" com as duas datas e o link para a grade em anteontem (`?data=`), ou em ontem quando anteontem é da semana anterior, que já saiu da grade. ontem é da tarefa aberta ou da semana que fechou ontem, que o job fecha antes desta etapa e que continua na grade até o fim do dia, então os dois últimos dias do período também cobram, inclusive na última semana do acompanhamento. anteontem pode ser da semana anterior, emendada nela: o último dia de uma semana e o primeiro da seguinte também são dois dias seguidos. a semana que o prescritor interrompeu, no arquivamento ou tirando a escala do acompanhamento, não cobra, e o diário enviado à mão depois do arquivamento cobra como os outros. sai um só por sequência de dias em branco: a tarefa guarda em `blank_days_reminded_until` o último dia cobrado, e a sequência só volta a cobrar depois de um dia preenchido. a sequência que passa para a semana seguinte, emendada na anterior, continua a mesma, então a tarefa sem dia cobrado olha o das semanas anteriores do mesmo diário. a semana que começa depois de dias sem tarefa nenhuma começa uma sequência nova. dia só com resposta anulada conta como em branco. a etapa roda depois do lembrete do prazo, e a tarefa que recebeu o lembrete do prazo no mesmo dia tem a sequência marcada sem aviso novo. o e-mail diz as datas e não diz qual formulário. trava o paciente e depois a tarefa, como o lembrete do prazo, e respeita o prescritor desativado e a preferência de e-mail do mesmo jeito (decisão de 14/11/2026, revisão das regras R6)
- cada um sai uma vez só, porque a consulta e a tarefa guardam em `reminder_sent_at` a data em que o aviso foi criado. a tarefa que ganha prazo novo (a enviada à mão que vira rodada, a do acompanhamento anterior que vira a primeira rodada do novo, a reaberta pela anulação, que fora do diário fica com pelo menos até depois de amanhã) volta a poder receber o lembrete, para o prazo novo. a consulta remarcada para outro horário também volta a poder receber (a edição que mantém o horário, não), e a remarcada para amanhã recebe na hora (veja consulta, acima)
- cada lembrete vai na própria transação, com o registro travado e lido de novo antes de sair: a consulta e depois o paciente, e no formulário o paciente e depois a tarefa (seção banco, ordem das travas). a consulta cancelada, remarcada ou anulada, a consulta do paciente arquivado e a tarefa respondida ou fechada pelo arquivamento antes de o job ler o registro não recebem lembrete. a mudança que chega depois do lembrete continua valendo, e o job não grava por cima o que a outra ação mudou. o lembrete na hora vai na transação da marcação, da confirmação ou da remarcação, que já travou a consulta (na remarcação e na confirmação) e o prescritor: o aviso e a data do lembrete entram depois, como o aviso de consulta remarcada, e o e-mail só sai depois que o banco confirma
- os três também vão por e-mail quando a conta está ativa e mantém os avisos por e-mail ligados no perfil, e com a mesma regra vão o cancelamento e a remarcação da consulta cujo lembrete já foi por e-mail (veja consulta, acima; decisão de 14/11/2026, revisão das regras R11). os outros avisos ficam só no sistema
- **faixa de idade:** o prescritor recebe *Paciente fez 18 anos* no job, uma vez por aniversário, com link para o histórico. o job olha quem fez 18 anos nos últimos 7 dias, então a api que ficou fora do ar não perde o aviso, e `patient.adult_notice_on` guarda o dia do aviso para ele não sair de novo. a data trocada no perfil que cruza os 18 anos avisa na hora (*Faixa de idade mudou*) e conta como esse aviso. o cadastro pelo convite avisa *Novo paciente vinculado* com a idade e, para menor, o nome e o parentesco do responsável legal (revisão das regras R9). o job trava o paciente e lê de novo antes de avisar, e o aviso toma a conta do prescritor em modo compartilhado depois, como os outros avisos (seção banco)
- o e-mail só sai depois que o banco confirmou o aviso. se o envio falhar, o aviso do sistema continua valendo, o e-mail não é tentado de novo e o log diz de qual conta era, pelo número e sem o endereço
- o horário do job vem de `api.acompanhamento.cron`, que por padrão é 8 da manhã
- cada etapa do job roda sozinha: se uma falhar, o log diz qual foi e as outras seguem. dentro da etapa cada acompanhamento, pedido vencido, pedido ainda sem resposta, tarefa vencida e lembrete vai na própria transação, e um item que falha não segura os outros: o log mostra o número dele, os outros saem mesmo assim e a etapa conta como falha, então o dia não fica concluído. o que já saiu fica gravado e não sai de novo, e o item que falhou é tentado de novo na próxima vez que o ciclo rodar. o lembrete da consulta de amanhã só vale naquele dia: o que falhou só sai se o ciclo rodar de novo no mesmo dia, na subida da api
- a api que estava fora do ar na hora do job roda as tarefas do dia quando volta, desde que já tenha passado do horário. o último dia concluído fica na tabela `daily_cycle`, e um dia com etapa que falhou não conta como concluído
- conta desativada não recebe escala nova do acompanhamento: a do paciente e a do prescritor pausam o envio até a conta ser reativada, e a rodada que ficou parada sai no job seguinte à reativação (revisão das regras R18)
- prescritor desativado pausa os lembretes dos pacientes dele, sem fechar nada: a tarefa pendente e a consulta marcada ficam como estão, mas o lembrete de formulário e o de consulta (aviso e e-mail) não saem enquanto a conta dele estiver desativada, porque ninguém leria a resposta. a conta do prescritor é lida depois da trava da consulta ou da tarefa, então a reativada antes de o job chegar nela já volta a receber, e o lembrete que ainda couber no prazo sai na rodada seguinte à reativação
- paciente arquivado não recebe o lembrete de consulta, porque saiu do tratamento, mesmo com a consulta marcada continuando na agenda; reativado, volta a receber. o job trava o paciente depois da consulta e só então lê o arquivamento, então o arquivamento gravado no mesmo instante aparece e o lembrete não sai, em vez de o aviso e o e-mail chegarem para quem acabou de ser arquivado. as escalas enviadas à mão depois do arquivamento continuam com lembrete, porque continuam chegando para ele

## painel inicial

| rota | o que faz |
| :--- | :--- |
| `GET /dashboard/patient/{id}` | próximas consultas, escalas esperando resposta com o prazo e o mesmo `answerPath` da central de escalas, a prescrição vigente e os avisos não lidos, com o total de escalas esperando resposta (`pendingScalesTotal`) e de avisos não lidos (`unreadNotifications`). os avisos e o total deles só vêm para o próprio paciente: o prescritor vê o painel sem a caixa pessoal dele |
| `GET /dashboard/prescriber/{id}` | pacientes ativos, avisos não lidos, consultas de hoje (cada uma com o `status`: na `CONCLUIDA` a tela mostra "Concluída" e "Ver histórico" no lugar de "Registrar", como a agenda. a prescrição e o Mini-Exame também deixam a consulta `CONCLUIDA`, com o registro vazio (seção agenda), e ela fica igual nas duas telas: o registro dela se preenche pelo "Editar registro" do histórico), pedidos de consulta esperando resposta e escalas vencidas sem resposta, com o total de pedidos (`waitingRequestsTotal`) e de vencidas (`lateScalesTotal`). paciente arquivado não entra nas vencidas: o arquivamento fecha as escalas abertas no dia e elas viravam alerta de quem já saiu do acompanhamento. a escala que o prescritor tirou do acompanhamento também não entra (seção escalas). sem outra pendente da escala, a resposta que chega depois de a última tarefa dela fechar como não respondida tira essa tarefa das vencidas no mesmo dia (seção escalas), e a anamnese tira toda avaliação inicial perdida (seção histórico clínico) |

cada lista traz no máximo cinco itens, porque o painel é um resumo, e o cartão leva para a tela que tem a lista inteira; as escalas vencidas ainda não têm uma tela com todas. nos quatro cartões que vêm com total (escalas esperando resposta, avisos não lidos, pedidos esperando resposta e escalas vencidas) o número é o total, contado no banco, e não o tamanho da lista, que para em cinco: quando a lista tem mais, o cartão diz "Mostrando 5 de N". as consultas de hoje não são cortadas, então o número delas é o tamanho da lista mesmo, e as próximas consultas param em cinco sem número e sem o aviso. nada aparece aqui sem origem no resto do sistema.

## indicadores do piloto

| rota | o que faz |
| :--- | :--- |
| `GET /indicators?from=&to=` | só prescritor: pacientes no ciclo de acompanhamento e formulários respondidos no prazo (meta de 70%), somando os pacientes dele, sem nome nem id de paciente (RF39) |

- sem datas vale os últimos 90 dias até ontem, e a resposta devolve o período usado
- só uma das datas, a inicial depois da final ou o fim em hoje ou depois dão 400: o prazo de hoje ainda está correndo
- pacientes no ciclo é a foto de hoje: acompanhamento automático valendo hoje (ativo e com o fim hoje ou depois, então o que terminou ontem sai antes do job das 8h), conta ativa e fora do arquivo. o total de pacientes ativos ao lado é do mesmo grupo: conta ativa e fora do arquivo
- os convites do período, sem os cancelados, viram enviados, cadastrados, que entraram em um acompanhamento e com o link ainda válido. convite vencido sem uso conta como enviado e não como em aberto
- o total são todas as tarefas do prescritor com o fim do prazo no período, avulsas ou do acompanhamento, seja qual for a situação delas: a regra olha as datas e as respostas ligadas, então não depende do job das 8h. o MEEM não vira tarefa e não entra, e a escala que o prescritor tirou do acompanhamento e fechou sem resposta também não, nem a favor nem contra (seção escalas), como a tarefa que ainda estava no prazo quando o paciente foi arquivado
- escala de período e avaliação inicial estão no prazo com `answeredAt` até o fim do prazo. a pendente com o prazo vencido e a avaliação inicial enviada depois do prazo contam como atrasadas, e também a tarefa não respondida que recebeu a resposta ou a anamnese depois de fechar, porque ela continua não respondida. a avaliação inicial que ainda estava no prazo no arquivamento fica de fora, mesmo com a anamnese chegando no mesmo dia depois de reativar: ela já fechou com o dia marcado no fim do prazo, e a anamnese atrasada marca um dia depois dele
- diário está no prazo com pelo menos um dia válido ligado à tarefa, a mesma regra que fecha a tarefa como respondida, mesmo pendente. o diário só com dias anulados fica fora do prazo. os dias preenchidos saem à parte, contra os dias do prazo. o dia preenchido depois de o job fechar a semana (a grade mostra a semana até o fim do dia seguinte) fica marcado como atraso (`filled_late`): conta nos dias preenchidos, mas não deixa a semana no prazo, e a semana que fechou sem nenhum dia continua `NAO_RESPONDIDA` (decisão de 14/11/2026, revisão das regras R6)
- resposta anulada não conta, porque a tarefa reabre e perde o `answeredAt`. a tarefa que voltou com o prazo vencido ganha prazo novo, fora do diário (pelo menos até depois de amanhã, seção escalas), e conta por ele: respondida de novo até esse prazo, está no prazo. anular a avaliação inicial não reabre a tarefa e ela continua contando
- nos formulários, paciente arquivado continua na conta. o arquivamento fecha as tarefas abertas pela regra da escala tirada do acompanhamento (seção escalas): a que já tinha vencido, com o job das 8h ainda sem rodar, conta como fora do prazo; a que ainda estava no prazo fica com o prazo encurtado para o dia e, sem resposta, ganha o dia marcado (`answered_at`) e fica de fora, nem a favor nem contra, porque quem interrompeu foi o prescritor (revisão das regras R22, 14/11/2026). antes ela contava como fora do prazo. a tarefa que o arquivamento encerrou, do acompanhamento ou enviada à mão antes dele, e cuja resposta é anulada depois também fecha assim e fica de fora, em vez de reabrir e contar como atraso. a desistência continua aparecendo pelas rodadas perdidas antes do arquivamento
- a porcentagem é arredondada para baixo e vem `null` quando não há nada para contar
- é número somado e não abre prontuário, então não entra na trilha de auditoria

## evolução

| rota | o que faz |
| :--- | :--- |
| `GET /progress/attributes` | o que dá para acompanhar num gráfico, com a escala, os limites do eixo, as faixas do instrumento, as âncoras das pontas (`lowAnchor`, `highAnchor`), qual lado é melhor (`higherIsBetter`) e de quantos em quantos dias a escala é respondida (`frequencyDays`: 1 na ficha e no diário, 7 no registro de dor e no de TEA, que falam da semana, e nulo na Hamilton, no Pittsburgh e no MEEM, que não têm frequência fixa), para o gráfico interromper a linha onde faltou resposta (decisão de 14/11/2026, revisão das regras R3). o do paciente vem sem o `ESCORE_MEEM` |

| `GET /patients/{patientId}/progress/comments?period=` | o que o paciente escreveu nas escalas do período, por data |

- `periodo` é `DIAS_15`, `DIAS_30`, `DIAS_60`, `DIAS_90` ou `TUDO`. o `TUDO` é o "todo o tempo" da tela de progresso, do paciente e do prescritor
- dia sem resposta não vira ponto no zero: ele simplesmente não entra na série (RN10)
- resposta anulada sai do gráfico e dos comentários, mas continua no histórico
- as âncoras são as do formulário da clínica: em ansiedade o 0 é "muito ansioso" e o 10 é "tranquilo", em dor o 10 é "dor intensa". no escore, as pontas são a primeira e a última faixa do instrumento. contagem e minutos não têm âncora no papel e vêm com `higherIsBetter` nulo, para a tela não inventar um lado melhor (RF20)
- acrescentar uma escala não pede mudança aqui: os atributos saem do catálogo das escalas (RNF08)

## guarda do prontuário

o prontuário tem guarda mínima de 20 anos (Lei 13.787/2018), então nenhuma rota apaga dado clínico. encerrar o acompanhamento de 90 dias é `PUT /patients/{patientId}/treatment-protocol/end` e só marca o protocolo como inativo; o acompanhamento que substitui outro fecha a rodada da escala que ficou de fora, mas também não apaga nada (seção escalas). as únicas rotas `DELETE` da api são a de notificação, que pertence à própria conta, e a de dia sem atendimento, que é só a agenda do prescritor.

## trilha de auditoria

| rota | o que faz |
| :--- | :--- |
| `GET /patients/{patientId}/audit-events?from=&to=&page=` | trilha de um paciente, para o prescritor dele |
| `GET /admin/audit-events?from=&to=&page=` | ações de prescritores, da administração e do sistema, para o administrador, sem nome de paciente, sem dizer qual registro clínico foi e com o número do paciente só nos eventos de conta |

- `from` e `to` são datas no formato `aaaa-mm-dd`, as duas inclusive. cada página traz 30 eventos, do mais recente para o mais antigo
- os serviços gravam quem criou, alterou ou anulou consulta, prescrição, anamnese, escala, designação e acompanhamento, na mesma transação da mudança
- abrir o prontuário também entra na trilha quando quem abre é o prescritor, uma linha por paciente a cada 30 minutos, contados da última linha gravada, também depois de a api reiniciar. baixar um arquivo é outra operação, `EXPORTACAO`, uma linha por arquivo (seção exportação)
- o que o job diário faz aparece com autor `Sistema`
- `detail` traz um texto curto, quando o evento tem: a troca da data de nascimento pelo paciente, com a antiga e a nova, como `Data de nascimento: 12/04/2010 → 12/04/2006` (revisão das regras R9); a exportação, com o tipo do arquivo e a marca da pesquisa, como `Consultas (appointments.csv), com identificação` (revisão das regras R19); e, da administração, *Busca da conta pelo e-mail* e *Lista das contas desativadas* (revisão das regras R20). nos outros eventos vem nulo, e na rota da administração ele some dos eventos de registro clínico, como a exportação (veja abaixo)
- o administrador não acessa dado clínico (RF30), e o `patientId` da trilha dele é o mesmo `id` que a busca de conta por e-mail devolve. por isso, na rota da administração, todo evento de registro clínico (escala, MEEM, anamnese, consulta, prescrição, designação, acompanhamento, abertura, arquivamento e exportação) sai como `recordType` `PRONTUARIO`, "Prontuário", sem o `patientId` e sem o `detail`, e só os eventos de conta (`CONTA_DE_PACIENTE` e `CONTA_DE_PRESCRITOR`) mantêm o tipo, o número e o detalhe. com o número, a busca de um e-mail mostrava a linha do tempo do tratamento daquela pessoa (revisão das regras R20). a trilha do prescritor continua com o tipo e o número de cada registro
- nos eventos de `CONTA_DE_PRESCRITOR` a rota da administração traz também `prescriberName`, o nome do prescritor dono da conta criada, corrigida, desativada, reativada ou com senha nova, que a administração já vê na lista de prescritores, e a tela mostra "conta de" e o nome. os nomes saem numa leitura só para a página inteira. nos outros eventos, e na trilha do prescritor, o campo vem nulo: o evento de conta de paciente continua só com o número
- a tabela `audit_event` só recebe inserção: o repositório não tem método de alterar nem de apagar, e nenhuma rota escreve nela

## erros

toda resposta de erro tem `timestamp`, `status`, `error`, `message` e `path`. erro de validação traz também `errors`, com a mensagem de cada campo.

| status | quando |
| :--- | :--- |
| `400` | dado inválido, parâmetro faltando ou regra de negócio violada |
| `401` | sem sessão, sessão vencida, sessão de conta desativada (com `X-Account-Deactivated`), sessão de outra conta que não a do `X-Session-User` ou senha errada |
| `403` | logado, mas sem permissão para aquele dado, conta desativada tentando entrar ou requisição com o cookie da sessão vinda de outro endereço |
| `404` | registro ou rota que não existe. a mensagem é genérica: o detalhe com o id vai para o log, não para a tela |
| `405` | método http que a rota não aceita |
| `415` | corpo enviado num formato que a rota não aceita. a api só recebe json |
| `409` | e-mail, CPF ou registro que já pertence a outra conta, com o campo em `errors`, só nas rotas da administração. o cadastro do paciente e a troca do e-mail de acesso não usam: um responde `400` sem dizer o campo e o outro responde igual exista ou não a conta |
| `429` | senha errada demais no login, na troca de senha ou de e-mail, pedidos demais de troca de e-mail ou de link de senha nova, ou cadastro recusado vezes demais |
| `500` | erro inesperado, registrado no log |

data com o ano fora do possível também é dado inválido e recebe `400` no campo: nascimento antes de 1900 e consulta ou anamnese antes de 2000. data no fim do calendário (`+999999999-12-31`), que o java lê mas não consegue somar um dia, e `page` acima de 100000 respondem `400` em vez de `500`. o id só de espaço na rota (`/patients/%20`, de um link copiado com espaço) também responde `400` com a mensagem de requisição inválida: o spring converte o id em branco para nulo e acusa a variável da rota como faltando. a variável que falta de verdade, de rota mal escrita, continua `500`. o endereço que o spring security recusa antes de ler a sessão, como o que tem ponto e vírgula (`/patients/3;x=1`, de um link colado com sujeira) ou barra dupla, também responde `400` com essa mensagem, escrita pelo `RequestRejectedHandler` do `SecurityConfigurations`. antes a recusa caía no `/error`, que roda sem a sessão, e a resposta era `401` com a sessão válida: a tela pedia login de novo, em laço.

`GET /health` responde se a api e o banco estão de pé. é o que o docker usa.

## banco

o esquema vem das migrações do flyway em `src/main/resources/db/migration/`. o hibernate só confere se as entidades batem com o banco, nunca altera nada.

- `V1__esquema_base.sql` consolida as migrações antigas numa base limpa, com restrições de nulidade e índices
- toda mudança de esquema é uma migração nova. nunca edite uma migração que já rodou em algum banco
- a regra do horário único (RN08) e a do registro único por dia no diário ficam no java, com trava pessimista na linha do prescritor e na do paciente, e não em índice do banco: o índice precisaria ser parcial (ignorando anuladas e o MEEM), e o h2 dos testes não aceita. a trava roda igual no h2 e no postgres
- essas travas são sql direto (`lockById`): com `@Lock` em jpql o hibernate trava prescritor e paciente (que herdam de `users`) numa consulta separada no h2, e pula essa trava quando a entidade já estava carregada na transação. os métodos de trava são `MANDATORY`: fora de uma transação a trava soltaria no fim do select sem ninguém perceber, então eles falham na hora
- o registro que vai mudar (consulta, receita, resposta de escala, anamnese e, nos jobs, a tarefa de escala) é travado com `RowLock.reload`: quem chega por uma rota já tem o registro na sessão, porque a checagem de acesso do `@PreAuthorize` carrega ele e o `open-in-view` segura a mesma sessão até a resposta. uma consulta com `@Lock` trava a linha mas não atualiza o que já estava carregado, e o serviço decidiria em cima do registro velho. o `reload` grava o que estiver pendente, tira a cópia velha da sessão e lê o registro de novo com a trava, que espera quem estiver mexendo nele terminar. o convite, que nenhuma checagem carrega antes, segue com `@Lock` normal (`findByIdForUpdate`)
- a ordem das travas é sempre consulta, depois prescritor, depois paciente, depois o registro do paciente que vai mudar (receita, resposta de escala, anamnese, tarefa de escala, acompanhamento), depois os registros da conta: `password_reset`, a própria conta (`users`) e `email_change`, nessa ordem. quem não precisa de uma delas pula, mas nunca volta para uma que vem antes. o convite fica antes de tudo: o cadastro pelo link trava o convite e só depois encosta no prescritor, pela chave do paciente novo, e o cancelamento trava só o convite. no postgres todo insert que aponta para o prescritor, o paciente ou a conta também toma a linha deles em modo compartilhado (a consulta, a resposta de escala, a tarefa e o acompanhamento apontam para o paciente e o prescritor, a trilha de auditoria para o paciente e a conta, e o aviso para a conta), e isso conta como encostar na linha. o insert sai na hora, então quem grava um desses trava antes o que vem antes na ordem: o registro da consulta feita fora da agenda trava o prescritor antes de gravar, e o MEEM trava a consulta e depois o prescritor. sem isso o insert tomava o paciente e ficava esperando o prescritor que o cadastro do acompanhamento ou a rodada segurava, enquanto eles esperavam o paciente. quem for travar algo novo segue essa ordem, senão duas transações ficam esperando uma pela outra. pelo mesmo motivo o job diário manda todos os envios de um acompanhamento antes de mexer na tarefa avulsa que vira rodada, e o arquivamento trava os pedidos de consulta em aberto do paciente (`RowLock`, em ordem de id) antes de travar o paciente, porque recusa esses pedidos. o pedido de consulta do paciente trava do mesmo jeito os pedidos dele em aberto, que ele substitui, e depois o prescritor e o paciente antes de gravar, então, com o paciente travado, nenhum pedido novo entra: o arquivamento conta os pedidos em aberto de novo e, se apareceu um que não estava na lista travada, é recusado para o prescritor tentar de novo, em vez de travar o pedido novo depois do paciente. o pedido do paciente faz a mesma conta e, se apareceu outro pedido dele, é recusado. a marcação do prescritor (`POST /appointments`) também trava o prescritor e depois o paciente antes de gravar, e com o paciente travado lê o arquivamento de novo no banco, então a consulta nova não entra para o paciente arquivado no mesmo instante
- o hibernate deixa os updates para o fim da transação, então a tarefa de escala, a receita substituída e o acompanhamento encerrado são gravados depois da trilha e do aviso, que já tomaram a conta em modo compartilhado, e no arquivamento também depois do update da própria conta. isso não fecha ciclo porque quem segura a conta de um jeito que barra o modo compartilhado (o `for update` da senha e do e-mail, e a troca do próprio e-mail) nunca encosta nesses registros, e o update comum da conta não barra a trilha nem o aviso. a renovação por cima do acompanhamento vencido, ou nos últimos 7 dias dele, é a exceção: o encerramento dele vai para o banco antes do insert do novo, ainda depois da trilha, porque o insert sai na hora e achava o anterior ativo, e o índice de um acompanhamento ativo por paciente do postgres recusava a renovação. quem muda várias linhas do mesmo tipo numa transação muda só as de um paciente, com a trava dele ou a do prescritor dele na mão (as tarefas no arquivamento e na rodada, as receitas que a nova substitui, os dias do diário que a tarefa nova pega), então duas transações não disputam essas linhas em ordens diferentes. nenhuma ação trava dois pacientes: a desativação do prescritor, que encerrava o acompanhamento de cada paciente dele, agora só pausa o envio e não encosta nos pacientes (revisão das regras R18)
- os jobs do dia leem a lista sem trava e mudam uma linha por transação, travando na ordem acima e lendo a linha de novo antes de decidir: a recusa do pedido vencido trava a consulta, o aviso do pedido ainda sem resposta também trava a consulta e depois grava o aviso para a conta do paciente, o lembrete de consulta trava a consulta e depois o paciente, o fechamento da tarefa vencida e o lembrete de formulário travam o paciente e depois a tarefa, e a rodada trava o prescritor e o paciente antes de ler o acompanhamento. o que uma rota gravou no mesmo instante (o cancelamento, a remarcação, a resposta, a anamnese, o arquivamento, o encerramento, a desativação) aparece, e o job pula aquela linha em vez de gravar por cima a cópia que leu antes. antes cada etapa ia numa transação só e gravava a linha inteira lida no começo: a consulta cancelada voltava para agendada com o lembrete, o pedido remarcado voltava para recusado e a resposta da tarefa vencida virava não respondida. e no postgres a trilha da recusa tomava o paciente antes da consulta, ao contrário do cancelamento, e o fechamento das tarefas e o lembrete gravavam várias tarefas do paciente numa ordem diferente da do arquivamento: nos dois casos as duas transações ficavam esperando uma pela outra
- a rodada do acompanhamento trava o prescritor e depois o paciente antes de ler o acompanhamento e as tarefas dele, na ordem acima: o cadastro trava os dois antes de ler o paciente, e o job trava o prescritor do paciente, que é para quem a tarefa nova aponta, só durante a transação daquele acompanhamento. sem a trava do paciente o job lia a tarefa enquanto o paciente respondia ela, e um gravava por cima do outro: a rodada voltava a tarefa respondida para pendente, ou a resposta desfazia o prazo novo da rodada. sem o prescritor antes, o job segurava o paciente e esperava o prescritor no insert da tarefa, enquanto o envio avulso segurava o prescritor e esperava o paciente, e as duas transações ficavam esperando uma pela outra no postgres. e lendo antes de travar, os dois seguiam com o que tinham lido: o job mandava a rodada para quem foi arquivado, teve o acompanhamento encerrado ou a conta desativada enquanto ele esperava a trava, e o cadastro deixava um acompanhamento ativo no paciente arquivado
- a tarefa de escala grava só as colunas que mudaram (`@DynamicUpdate`): o lembrete do job e a resposta do paciente mexem em colunas diferentes dela, e o lembrete gravado em cima da tarefa lida antes da resposta voltava a tarefa para pendente
- a regra da conta: nada que segura a trava da conta (`UsersRepository.lockById`, um `for update` em `users`) encosta no paciente depois, nem por insert com chave estrangeira para ele, como a trilha. o `for update` barra até o modo compartilhado, e a resposta de escala trava o paciente e depois grava a trilha com o paciente como autor, que toma a conta: quem trava a conta e depois encosta no paciente fica esperando a escala enquanto a escala espera a conta, e o postgres derruba uma das duas. o pedido de e-mail novo e a troca de senha (pelo perfil ou pelo link) travam a conta e não encostam no paciente. o pedido e a troca pelo perfil travam a conta antes de ler a senha atual: a senha que o link gravou no mesmo instante aparece, e quem só sabe a senha antiga é recusado em vez de gravar a senha dele por cima. a confirmação do e-mail grava a trilha apontando para o paciente, então numa conta de paciente ela trava o paciente antes de tudo (`PatientRepository.lockById`, que numa conta de prescritor ou da administração não acha linha e não trava nada) e só depois o `password_reset`, a conta e o `email_change`
- gravar o paciente pelo hibernate grava a conta antes: o `updated_at` e os campos de `users` vão num update e os de `patient` em outro, nessa ordem. por isso toda ação que grava na conta de um paciente e também encosta no paciente (gravando nele ou pela trilha) trava o paciente antes de ler, igual à escala: o perfil e o aceite do termo (o responsável, o nome social), a ativação ou desativação pela administração (a trilha aponta para o paciente) e o arquivamento e a reativação do prontuário. sem isso elas seguravam a conta esperando o paciente que a confirmação do e-mail travou, enquanto a confirmação esperava a conta. na ativação e no arquivamento o postgres já tomava o paciente pela trilha antes da conta, mas só porque o insert da trilha sai antes do update da conta, e no h2 o arquivamento ficava preso com a confirmação. o mesmo vale para quem encosta na conta só pela trilha ou pelo aviso e também encosta no paciente: o cancelamento da consulta trava o paciente logo depois da consulta, e a correção da anamnese trava o paciente antes da anamnese, igual à correção da escala. sem isso a trilha com o paciente como autor tomava a conta em modo compartilhado e ficava esperando o paciente que a confirmação travou, enquanto a confirmação esperava a conta. a anulação da anamnese, do prescritor, não encosta na conta do paciente, mas trava na mesma ordem da correção, senão uma ficava com a anamnese esperando o paciente e a outra com o paciente esperando a anamnese. a anamnese nova também trava o paciente antes de tudo, mas por outro motivo: ela dá baixa na tarefa da avaliação inicial, então segue a mesma ordem do job que fecha a tarefa vencida, paciente e depois a tarefa (seção anamnese). a saída da conta, a preferência de e-mail, o pedido de e-mail novo e a troca de senha só mexem na conta e não travam o paciente. todas essas gravações contam com o `@DynamicUpdate` das contas (seção perfil), que grava só as colunas mudadas
- isso conta com o `READ COMMITTED` padrão do postgres: depois que a trava libera, a leitura seguinte enxerga o que a outra transação gravou. em `REPEATABLE READ` a corrida voltaria sem ninguém perceber
- quem anula, analisa e arquiva é sempre prescritor, e as relações `annulledBy`, `reviewedBy` e `archivedBy` têm esse tipo de propósito: como `Users`, o hibernate criava um proxy genérico e avisava "narrowing proxy" quando o mesmo prescritor era carregado como `Prescriber` na mesma sessão. o autor da trilha continua `Users` (pode ser a administração) e vem junto na consulta da lista, já com o tipo certo. o `DevDemoDataTest` e o `MainScreensWithDemoDataTest` contam esses avisos e falham se aparecer algum

## testes

```bash
./mvnw clean install
```

com `-Pdocs` a suíte inclui o teste da documentação da api, igual ao ci.

os testes rodam no perfil `test`, com h2 em memória, então não precisam de postgres nem de variável de ambiente. todo teste que sobe o contexto do spring precisa de `@ActiveProfiles("test")`.

testes de fluxo que envolvem job agendado ou serialização de resposta devem rodar sem `@Transactional`: a transação do teste esconde carregamento sob demanda que falharia em uso real. o `MainScreensWithDemoDataTest` (telas) e o `ClinicalActionsWithoutTestTransactionTest` (rotas que gravam) fazem isso para as rotas principais.

os testes de corrida (`AgendaRaceTest`, `ScaleResponseRaceTest`, `ClinicalRecordRaceTest` e `AnamnesisRaceTest`) seguram a trava numa transação de fora, pelo `HeldLock`, disparam o fluxo numa thread e conferem que ele espera. a url do h2 de teste leva `LOCK_TIMEOUT=10000` por causa deles: com o padrão de 2 segundos o fluxo que espera cairia por tempo esgotado.

os jobs do dia entram nesses testes do mesmo jeito: a recusa do pedido vencido e o lembrete de consulta esperam a consulta que o cancelamento ou a remarcação segura, o fechamento da tarefa vencida espera a resposta e a anamnese, e o lembrete de formulário e a rodada esperam o arquivamento. o arquivamento espera o pedido de consulta que a confirmação segura e mantém a consulta confirmada, sem recusar. o pedido do paciente, a marcação do prescritor e o lembrete de consulta esperam o arquivamento que segura o paciente: o pedido e a marcação são recusados e o lembrete não sai. o arquivamento que espera o paciente enquanto um pedido novo é gravado é recusado sem gravar nada e, na segunda vez, recusa o pedido. dois pedidos, ou duas trocas, do mesmo paciente no mesmo instante terminam com um só esperando resposta, e a troca espera o pedido antigo que a confirmação segura, mantém a consulta confirmada e é recusada, sem cancelar nem gravar nada. o cadastro do acompanhamento e a anamnese nova também esperam o arquivamento e são recusados, a segunda anulação da receita espera a primeira, a anulação da receita espera a correção do registro que segura a consulta e mantém a consulta concluída, e o registro da consulta e o MEEM esperam o prescritor que o cadastro do acompanhamento segura. alguns impasses só o postgres monta, porque no h2 a chave estrangeira não toma a linha apontada: o registro da consulta e o MEEM contra o cadastro do acompanhamento e a recusa do pedido contra o cancelamento. no h2 esses testes pegam o fluxo que não espera a trava (ou que grava por cima), e o impasse mesmo aparece no job `backend-postgres` do ci, onde a transação de fora faz o que a outra ação faz. o impasse entre o arquivamento e o job que gravava várias tarefas nenhum teste monta, porque depende das duas gravações no mesmo instante; o teste confere que o lembrete espera o arquivamento.

o `EmailChangeRaceTest` usa o mesmo `HeldLock` para a ordem paciente, depois conta: segura o paciente como a escala e confere que a confirmação do e-mail espera e as duas terminam, e segura o paciente como a confirmação e confere que o perfil, o aceite do termo do menor, a desativação, o arquivamento, o cancelamento do pedido pelo paciente e a correção e a anulação da anamnese esperam. no h2 a chave estrangeira não toma a linha apontada, então a corrida da escala com a confirmação só vira impasse de verdade no postgres (o job `backend-postgres` do ci); no h2 o teste pega a confirmação que não espera o paciente. sem a trava do paciente o perfil e o aceite viram impasse nos dois bancos, porque gravam a conta com update antes do paciente. ele também segura a conta como o link de senha nova e confere que a troca de senha pelo perfil espera e confere a senha atual com a senha nova.

as corridas na linha da conta não têm trava para esperar, então o `ProfileRaceTest` lê a conta numa transação, deixa a outra ação gravar numa transação nova e só depois roda o fluxo na transação de fora, que continua com a conta lida antes. o `LogoutRaceTest` faz o mesmo com um espião do `UsersRepository`, porque a saída lê a conta e grava sem nada no meio.

## padrão de código

vale para todo código novo ou reescrito:

- dto de entrada e saída em toda rota, nunca a entidade
- o serviço devolve a resposta pronta (dto), montada dentro da transação dele, e o controller só repassa. o `open-in-view` fica desligado, então ler paciente ou prescritor fora do serviço quebra em uso real, mesmo passando nos testes com `@Transactional`
- regra de negócio no serviço, com `@Transactional`
- nomes em inglês, em camelCase e descritivos
- comentários curtos, em minúsculas, sem acento e sem pontuação

## situação dos módulos

a fundação (configuração, erros, sessão, administração e migração base), o módulo de acesso e identidade (login, convite, cadastro, termo de consentimento, perfil e recuperação de senha), o de autorização (perfil e vínculo em toda rota, fim da exclusão de dado clínico e trilha de auditoria), o de atendimento (consulta, prescrição, anamnese, histórico e arquivamento de paciente), o de agenda (horários de atendimento, pedido do paciente e agenda do prescritor) o de escalas (motor único, tarefas com prazo e acompanhamento automático de 90 dias) o de evolução (gráfico com a faixa do instrumento, a dose e o relato do paciente) o painel inicial de cada perfil, os avisos com lembretes automáticos e a exportação já seguem o padrão novo. a remodelação cobriu todos os módulos da ordem de trabalho do §8.6 do documento de requisitos. o `open-in-view` fica ligado porque vários controllers montam a resposta depois do serviço, e o `MainScreensWithDemoDataTest` abre as telas principais sem a transação dos outros testes para pegar esse tipo de erro.
